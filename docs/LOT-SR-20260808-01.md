## BUILD

### 1. Live T-MINUS countdown (time tracking)

`CalendarWidget.tsx` gains a `now` tick state, updated every 1s **only while
the panel is open** (`document.hidden` guard, matches the visibility-gating
convention already used in `EvolutionMilestoneToast` / `ContextualPromptsWidget`).
Renders `T-MINUS HH:MM:SS` (or `NdD HH:MM:SS` past 24h) counting down to the
next upcoming entry's date, or `T-0 · ARRIVED TODAY` once the date lands.
Collapsed widget costs nothing — no interval runs.

### 2. CAL-ALERT: military-grade arrival notification

A second effect scans entries for ones whose date equals today, on mount and
every 60s (also `document.hidden`-gated, catching midnight rollover on a
session left open). First arrival writes a `calendar_alert` log:

```
text:     [ALERT] <type>: <text> (ARRIVED <full date>)
event:    calendar_alert
metadata: { date, text, entryType }
```

Dedup is client-side via `localStorage['lot-calendar-alerted-v1']`, a capped
(300-entry) array of `date::type::text` keys — survives reloads, so an
arrived entry alerts exactly once regardless of remounts.

### 3. Logs.tsx — CAL-ALERT: handler

New `calendar_alert` case renders in the existing military instrument style
(uppercase tracking-widest label, opacity-tiered instrument rows), consistent
with every other event handler in the file:

```
CAL-ALERT:
  <TYPE> ARRIVED
  <entry text>
  <date>
```

Also fixed a completeness gap in the existing `calendar_entry` (`CAL:`)
handler — it read `metadata.text` at creation time but never rendered it,
so the LOG showed only the entry type and date. Added the text row.

### 4. TODAY panel

Upcoming-entries list now shows `Today` (uppercase, tracking-widest) in place
of the full date string for entries whose date has arrived, both in the
open-calendar T-MINUS line and the collapsed upcoming list — the "today
panel" from the original Calendar Alerts scope, expressed as a label change
rather than a new UI section (keeps the widget minimalist).

### 5. Backend Whitelist Hygiene (doctrine clause, cited not restated)

`calendar_alert` added to `displayableEvents` in `routes/api.ts` in the same
commit as the handler — this is the exact failure class the doctrine clause
of that name already names (SR-20260604-01 founding case: `calendar_entry`
itself). Caught proactively during this session rather than discovered later
as a CRITICAL FIX. See DISTILL block below — doctrine cited, not re-derived.
