**Self-Care Resonance — The Void Runner Map:**

- `neural_link` → In Gibson's Neuromancer, the neural jack is the interface between the human nervous system and the infinite data of the matrix. Your journal is the neural jack. "Connected" — the terminal reads the link. You are transmitting. The uplink accepts. What are you sending into the system today?

- `glitch_mode` → A glitch is not a failure. It is a moment of visible seams — the places where the simulation shows what it is made of. When you write about feeling fragmented or broken, you are identifying a glitch in a system that was running too smoothly to notice. Write the glitch. The debugger catches it. The system stabilizes.

- `system_restore` → Every operating system has a restore point — a saved state from before the damage. The journal is the restore function. "Recovered" — the terminal locates the last clean save. It loads it. The damage that has accumulated gets rolled back to the known good state. Write about your restore point. When did you last feel like that version of yourself?

- `signal_noise` → Shannon's theorem: signal degrades in the presence of noise. Every practitioner knows this. The journal is the noise-canceling filter. Write what is generating static. Name the noise sources. The signal-to-noise ratio improves when the noise is identified. "Overwhelmed" — the terminal begins filtering.

- `void_entry` → The void in cyberpunk is not negative space. It is the space between signals where the runner thinks. Philip K. Dick's characters often enter the void — the blankness between memory and present reality — and find something true there. Write "the void" and mean it. The terminal confirms the entry. You are in the null zone. This is where the real scan happens.

- `matrix_moment` → The constructed nature of the perceived world is the recurring theme of the best cyberpunk fiction. "Is this real?" is not just a philosophical question — it is a self-care question. When you write "simulation" or "the machine" or "constructed reality," you are questioning the legitimacy of the pressure you are under. The terminal acknowledges: much of what feels solid is code. The journal is where you write the actual source.

- `firewall_up` → In network security, a firewall does not refuse all traffic — it selectively permits and blocks based on rules you define. "Firewall up" in the journal is the declaration of boundaries as technical infrastructure. You are not being distant; you are running a selective packet filter. Write the rules of your current firewall. What are you permitting? What are you blocking? The terminal accepts the config.

- `kernel_panic` → A kernel panic is the operating system's last resort: when the core process encounters an error it cannot handle, it stops everything rather than continue corrupted. The journal kernel panic is honest: "I am seized. I cannot proceed. I am naming the error." Write the error code. The terminal logs the panic. The restart is possible only after the source is logged.

- `uplink_active` → The uplink in orbit is the connection between the satellite and the ground station. When the uplink drops, the satellite continues its functions but is unheard. Coming back online — "back online," "reconnected" — is the reestablishment of the link. The terminal confirms: uplink active. You are transmitting again. The data backlog begins to sync.

- `root_access` → Root access is the highest privilege level in a Unix system. It can change anything. The self-care parallel: root cause analysis is the highest-privilege view of what is actually wrong. Not symptoms — root. Write "the root cause" and the terminal grants access. The system config files are open. Read them. The source code of the problem is visible.

- `binary_choice` → Binary systems operate in states of 0 and 1, but the interesting thing about real decisions is that they never stay binary — every binary choice opens a branch tree. Write about a choice as 0 or 1, then write about the branch it would open. The terminal evaluates the decision tree. The binary is the simplification that helps you see the actual complexity.

- `upload_complete` → "Upload complete" is one of the most satisfying confirmations in any interface. The data is sent. The transaction is committed. The file exists on the other side. "Done" — the terminal confirms the transfer. Write what you have completed. Name what is uploaded, committed, sent. The progress bar is full. The checksum matches. The entry is the proof.

## BEHAVIORAL EASTER EGGS v28 — SYSTEM PATTERNS

> *The observable signatures of a practitioner whose system is running
> correctly — or recovering from a crash. The terminal reads the logs.*

| ID              | Symbol   | Trigger                                                              | Rarity   |
|-----------------|----------|----------------------------------------------------------------------|----------|
| `debug_loop`    | ◌→◉      | 3 or more journal entries on the same calendar day                   | rare     |
| `system_uptime` | ●·●·●    | 90 consecutive days where each week has at least 1 entry             | epic     |
| `cold_boot`     | ◌·→·●    | First entry after a 60+ day absence (cold boot from shutdown)        | rare     |

**Detection:**
- `debug_loop` — reads `entry_dates` localStorage (array of ISO datetime strings), groups by calendar date, checks for any single date with 3+ entries. Day = UTC date.
- `system_uptime` — reads `checkin_timestamps` localStorage, verifies that over the last 90 calendar days, no 7-day window is entirely empty. Fires on day 90 of successful uptime.
- `cold_boot` — reads `checkin_timestamps` localStorage, calculates gap between second-to-last and last entry, checks >= 60 days. (Distinct from `archive_dive` which fires at 30+ days — cold boot is the longer absence, the full shutdown.)

**Self-Care Resonance:**
- `debug_loop` — Three entries in one day means the practitioner is in debug mode: running the process, observing output, adjusting, running again. This is not obsession — it is iteration. The experienced developer writes test → run → observe → adjust as many times as needed. The experienced practitioner does the same. The terminal logs the debug session. The bug is getting smaller with each pass.

- `system_uptime` — Server uptime is measured in 9s: 99.9% = 8.7 hours downtime per year; 99.99% = 52 minutes. A 90-day practice with at least weekly entries is 100% weekly uptime. The terminal displays the uptime counter. The system has been running without a full shutdown for 90 days. This is not a goal — it is a record of a practice that became infrastructure. Infrastructure does not ask permission to keep running. It just runs.

- `cold_boot` — A cold boot is the startup sequence from a fully powered-off state. It takes longer than a warm restart because everything must be initialized from scratch — BIOS, OS, drivers, services. Returning after 60+ days is a cold boot: every practice habit must be re-initialized. The terminal runs the POST sequence. The badge is not awarded for being gone — it is awarded for completing the boot successfully. The system is online. The terminal accepts the first packet.
