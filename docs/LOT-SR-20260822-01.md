### What changed, concretely

**`CalendarWidget.tsx`** — time tracking:
- `CalendarEntry.time?: string` (HH:mm) — an optional clock time alongside
  the existing date, stored in `Log.metadata.time`, entered via a native
  `<input type="time">` next to the existing text field in the add-entry form.
- `entries` sort now breaks date ties by time, so same-day entries with a
  scheduled time order correctly.
- Both the per-date entry list and the upcoming-entries list now render the
  time (dim, `tabular-nums`) next to the entry text when set.

**`CalendarWidget.tsx`** — reliable due-check:
- A `React.useEffect` runs a check on mount and every 30s (mirrors the
  existing 30s cadence used by `EvolutionMilestoneToast`): for every entry
  dated today whose time has arrived (or that has no time set, which fires
  immediately once its day arrives), it fires an alert exactly once.
- Deliberately scoped to `date === today` only — NOT `date <= today` — so
  the very first check after this ships never floods the log with alerts
  for the entire pre-existing backlog of undated-time calendar_entry rows.
  This was checked explicitly before landing: a `date <= today` condition
  would have retroactively alerted on every historical entry the moment this
  code shipped, since none of them have a `time` set.
- Dedup is **not** local/session state — it is read back from the Log
  itself (`alertedKeys`, derived from existing `calendar_alert` rows'
  `metadata.entryKey`). A page reload, a different tab, or a different
  device all see the same already-fired set. A `firingRef` in-flight guard
  additionally prevents a double-submit within one race window while a
  createLog round-trip is still pending.
- Known limitation, recorded honestly rather than silently: two browser
  tabs open at the same due moment can both pass the `alertedKeys` check
  before either write lands, producing two `calendar_alert` rows for the
  same entry (no DB unique constraint exists on `logs.metadata`, and adding
  one was out of scope for a client-side widget session). Low blast radius
  — worst case is a duplicate log line, not a data-integrity issue.

**`CalendarWidget.tsx`** — the "military-grade" notification itself:
- On fire: writes a `calendar_alert` Log (`[ALERT] <TYPE> DUE: <text> (<date>
  <time>)`), records a `recordCalendarAlertSignal` QIE signal, and shows an
  in-widget banner (`Tag` "ALERT" + uppercase tracking-widest label + dismiss
  button) for 12s or until manually dismissed.
- Deliberately did **not** build a new toast/overlay system or wire the
  browser `Notification` API. Neither exists anywhere in this codebase today
  (confirmed by grep — zero hits for `new Notification`/
  `Notification.requestPermission`), and "military-grade" already has a
  concrete, established meaning here: the `Block label="XXX:"` convention
  used by every other Log event type (`CAL:`, `DRCT:`, `PHR:`, `ARCH-SHIFT:`,
  ...) — terse all-caps field-manual-style tags. `ALERT:` follows that
  convention exactly rather than introducing a new visual language.

**`Logs.tsx`** — new `else if (log.event === 'calendar_alert')` branch,
sibling to the existing `calendar_entry` (`CAL:`) branch, rendering
`Block label="ALERT:"` with TYPE/STATUS/TEXT/DATE+TIME fields in the same
`opacity-30`/`opacity-60`/`tabular-nums` vocabulary as its neighbors.

**`intentionEngine.ts`** — `recordCalendarAlertSignal(entryType, date, text)`,
a thin wrapper mirroring the existing `recordCalendarSignal`, under
`source: 'log'` (no change to the closed `IntentionSignal['source']` union
was needed or made).
