WHAT CHANGED, PRECISELY:
- logTriggers.ts: added `StoryPeriod` type and `parseStoryPeriod(text)`,
  a pure parser for an optional `day|week|month|year` argument after
  `/story`. Kept as a pure function (no stores, no DOM) per the file's
  existing design rule, so it stays testable in isolation.
- Logs.tsx (NoteEditor): the `story-mode` trigger handler now calls
  `parseStoryPeriod(value)` and forwards `period` to `submitStory`; the
  command-stripping regex now also strips an optional period word so it
  isn't sent to the AI engine as literal log text. `/system`'s help output
  now lists the three new period variants.
- queries.ts: `useStoryGeneration` request type gained an optional
  `period?: 'day' | 'week' | 'month' | 'year'` field — additive, no
  breaking change to the bare `/story` call shape.
- api.ts (`POST /story`): added a `PERIOD_CONFIG` table (days-back window,
  Log query limit, sample size per data category, and a human label per
  period). When a period is present, the `Log.findAll` query now filters
  `createdAt >= now - N days` via `Op.gte` instead of an undated
  "last 200 rows" scan, the per-category sample size scales from 10 (bare
  /story) up to 60 (year), the system prompt explicitly instructs the model
  to compress the named window into "a through-line, not a list of events"
  rather than the previous generic "recent journey" framing, the word
  budget scales from 100-200 (bare/day/week) to 150-300/350 (month/year),
  completion token budget rises from 512 to 768 for period requests, and
  the persisted `generated_story` Log now records `period` in its metadata
  (`'recent'` for the bare-command path, preserving prior behavior exactly
  for existing callers).
