## DISCOVERY — WHAT ALREADY EXISTS

The S-2 brief describes three know-how items. Before writing anything, this
session read the live Log surface (`src/client/components/Logs.tsx`,
`src/client/utils/logTriggers.ts`) and the server route layer
(`src/server/routes/api.ts`) to find out how much of the brief was already
built, per the skill's "discover, don't assume" rule:

```
1. Environment context on every click (weather, time, humidity, sky,
   location, astrology) recorded as a context snapshot with no photo/audio
   — CONFIRMED PRESENT. `getLogContext()` attaches context to every Log
   row; `LogContainer`/context widgets already surface it.

2. Passive Journal UI — user types, no prompts, no questions; the machine
   only follows up on a detected spike or pattern change — CONFIRMED
   PRESENT AS A PATTERN, DIFFERENT MECHANISM THAN "SPIKE DETECTION" NAME
   SUGGESTS. The Log input itself has zero prompts. Follow-up currently
   comes through two channels: (a) the Memory Engine's question-generator
   (src/server/utils/memory/question-generator.ts), which asks
   progressively deeper follow-ups on a cadence, and (b) the QIE
   (src/client/stores/intentionEngine.ts), which recognizes behavioral
   patterns client-side and recommends widgets. Neither is literally
   "detect a numeric spike in a signal series and re-open that entry" —
   this is the gap most worth a future session's attention, flagged below
   rather than built blind this session (see NEXT).

3. Compressed story of day/week/month/year, sent back to further compress
   the loop — PARTIALLY PRESENT. /story and /system were BOTH already
   live: `logTriggers.ts` already defines the `story-mode` and
   `system-help` triggers, `Logs.tsx` already renders the STORY and
   SYSTEM blocks, and POST /api/story already calls the Together AI
   engine via `aiEngineManager.getEngine('together')` on real log/mood/
   self-care data (LOT User data -> QIE state passed as `quantumState`/
   `userIndex` -> Together AI -> Log row `event: generated_story`,
   matching the S-2 pipeline diagram exactly). What was MISSING: the
   "day/week/month/year" period explicitly named in the brief. The route
   always compressed a fixed ~10-entry recent window with no period
   concept. This session's BUILD closes that gap.
```

## NOTE — ARCADE (GAMIFIED) EVOLUTION LAYER

Per the S-2 brief's instruction to note this explicitly: the badge system
(`src/client/utils/badges.ts`, 800+ badge types as of the v32 Hero's
Journey Codex — see `docs/badges/`) is this self-care product's arcade
layer. It is not a bolted-on minigame; badges unlock from the same signals
the passive Journal and QIE already read (word choice, check-in cadence,
streaks, calendar coincidences), so earning one is a side effect of using
the Log honestly rather than a separate objective. Read plainly, this is
the product's stance on gamification: self-care software that rewards
engagement without asking the operator to perform for the reward. Recorded
as doctrine clause D-005 (marked PROVISIONAL — see LOT-DOCTRINE.md) rather
than asserted as a finished design conclusion, since this session read the
code but did not verify the claim against user-facing behavior in a
browser.
