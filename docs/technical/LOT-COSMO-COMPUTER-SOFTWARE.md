--------------------------------------------------------------------------------
01 // WHAT THE BRIDGE IS
--------------------------------------------------------------------------------

The Bridge is the software half of the LOT API Connector
(LOT-COSMO-COMPUTER-v1.md Section 06). It is the only piece of this system
that holds real credentials to lot-systems.com. It runs as a lightweight
companion process — phone app or desktop tray app — already signed into the
operator's LOT account, and it is the thing that makes a $10 microcontroller
usable against a JWT-cookie web app without teaching the microcontroller to
speak TLS session auth.

  RESPONSIBILITIES
    - Hold the Device Pairing Token (scoped to POST /api/logs only).
    - Poll or subscribe for outbound notifications generated by LOT's AI
      engine for this operator, and relay them to the paired Terminal over
      BLE/local Wi-Fi.
    - Receive COPY_EVENT and WEATHER_SAMPLE messages from the Terminal
      (docs/technical/LOT-COSMO-COMPUTER-FIRMWARE.md Section 02) and turn
      them into real API calls.
    - Own pairing (Section 03) and OTA delivery (firmware doc, Section 07).

  NOT RESPONSIBILITIES
    - No UI beyond pairing/status. The Bridge is infrastructure, not a second
      app surface competing with lot-systems.com itself.

--------------------------------------------------------------------------------
02 // THE LOT API CONNECTOR — CONCRETE CALLS
--------------------------------------------------------------------------------

Built directly against the live endpoints already shipping in this
repository — not a new API surface invented for hardware.

  COPY EVENT -> LOG TAB
    On COPY_EVENT from firmware (text, displayedAt, pressedAt):
    ```
    POST /api/logs
    {
      "text": "<the notification text that was on the Terminal's screen>",
      "event": "cosmo_terminal_copy",
      "metadata": {
        "deviceId": "<paired Terminal's device id>",
        "displayedAt": "<ISO timestamp>",
        "pressedAt": "<ISO timestamp>"
      }
    }
    ```
    This is the same request shape `useCreateLog` sends from the web client
    (src/client/queries.ts, line 139-142). The entry then appears in the
    operator's Log tab at the existing `/log` route
    (src/client/stores/router.ts, line 31) — no new tab, no new UI, the
    Terminal writes into the Log tab that already exists.

  WEATHER SAMPLE -> CROSS-CHECK
    On WEATHER_SAMPLE from firmware, the Bridge does NOT write a log entry
    per sample (that would flood the Log tab). It forwards the reading to a
    LOT-side comparison against the existing weather service
    (src/server/utils/weather.ts) and only surfaces a notification (Section
    03, reverse direction) when local and forecast conditions diverge beyond
    a threshold — this is the mechanism described in
    LOT-COSMO-COMPUTER-v1.md Section 04.

  OUTBOUND NOTIFICATION -> TERMINAL
    The Bridge subscribes to (or polls) the AI engine's decision of WHAT/WHEN
    to notify this operator (LOT-COSMO-COMPUTER-v1.md Section 04's diagram).
    v1.0 implementation detail (server-side polling endpoint vs. push) is
    intentionally left open pending a short server-side design pass — this
    document specifies the Bridge's role and payload contract, not a new
    server route; opening that route is next-session scope, flagged here so
    it is not silently assumed done.

--------------------------------------------------------------------------------
03 // PAIRING FLOW (v1.0 — MANUAL; v1.1 — QR, SEE FIRMWARE DOC SECTION 05)
--------------------------------------------------------------------------------

```
1. Operator installs Bridge, signs in with existing LOT account (reuses
   existing web session/auth — no new account system).
2. Operator requests a Device Pairing Token from LOT account settings
   (LOT-COSMO-COMPUTER-v1.md Section 06) — scoped, revocable, POST /api/logs
   only.
3. Bridge enters BLE scan mode; unpaired Terminal advertises (firmware doc,
   Section 02, "PAIR ME" state).
4. Bridge and Terminal exchange a link key over BLE; Bridge stores the
   Device Pairing Token association locally, Terminal stores nothing more
   than "I am paired to this Bridge."
5. Bridge confirms pairing by sending a test notification ("COSMO Terminal
   paired.") — first real end-to-end proof the loop works before the
   operator leaves setup.
```

--------------------------------------------------------------------------------
04 // REVOCATION + SAFETY
--------------------------------------------------------------------------------

Revoking the Device Pairing Token from LOT account settings immediately cuts
the Bridge's ability to write to /api/logs — the Terminal keeps working
locally (still shows the last message, button still registers a local press)
but nothing reaches lot-systems.com until re-paired. This mirrors the
"human gate on notify-class actions" posture already documented for LOT's own
server (docs/corporate/LOT_Autonomous_AI_Server.md, Section 04) — a scoped,
revocable token instead of a device holding a standing master credential.
