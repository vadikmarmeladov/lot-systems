# LOT Node — Software / LOT API Connector

This is the document that ties the physical device to the existing
lot-systems.com backend. Everything below is checked against the actual
code in this repository as of this session, not assumed.

## 1. What exists today vs. what needs to be built

| Capability | Status |
|---|---|
| `GET /api/logs` — read a user's log stream | **Exists** (`src/server/routes/api.ts:1082`) |
| `POST /api/logs` — create a log entry `{text, event, metadata}` | **Exists** (`src/server/routes/api.ts:1563`) |
| Log tab UI rendering `note`/`weather_update`/etc. events | **Exists** (`System.tsx`, `useLogs` hook) |
| Per-user weather caching (`WeatherResponse` model) | **Exists** — device weather readings should slot into the same concept |
| Auth for a **browser session** (JWT cookie, `JWT_COOKIE_KEY`) | **Exists** (`src/server/routes/auth.ts`, `.env.example`) |
| Auth for a **non-browser device** (long-lived personal access token) | **Does not exist yet — must be built** before any device can call `/api/logs` |
| Server → device push channel (for pager-style notifications) | **Does not exist yet — must be built** |
| `hardware_copy_signal` (or similar) as an allowed `event` value | **Does not exist yet** — the `/logs` GET handler filters to an explicit allow-list of event strings (`src/server/routes/api.ts:1084-1179`); a new event type needs to be added to that list to be visible in the Log tab |

This matters: the device cannot integrate against the LOT API as-is today.
Two small, additive server changes are required first. Neither touches
existing behavior.

## 2. LOT API connector — device authentication (to be built)

Recommended approach: a **device personal access token**, not the browser
JWT cookie flow (cookies don't fit a headless device).

- Add a `DeviceToken` model: `{ id, userId, token (hashed), label, createdAt, lastSeenAt }`
- Issue one token per paired device from the user's Settings page
  (`https://lot-systems.com/settings` → "Devices" — new UI, not built yet)
- Device stores the token in encrypted NVS (see `FIRMWARE.md` §4) and sends
  it as `Authorization: Bearer <token>` on every request
- Add fastify middleware that accepts either the existing browser JWT
  cookie **or** a valid device bearer token, resolving to the same
  `req.user` object the rest of `api.ts` already expects — this means
  `POST /api/logs` needs zero changes to its own handler once this
  middleware exists.

This is the same shape as most consumer-hardware "companion API" designs
(a scoped, revocable, per-device token) and keeps the device from ever
holding the user's real password or full-session cookie.

## 3. Pager-like notifications (brief item 2, and the standalone "Simple
screen..." requirement)

Two candidate designs; **recommendation: Option B** for v1.

**Option A — WebSocket/MQTT push.** Lowest latency, but requires a new
persistent-connection server component and a device-side MQTT/WS client
library, plus handling reconnects on flaky Wi-Fi. Higher build cost for v1.

**Option B — Short poll (recommended for v1).** Device calls
`GET /api/devices/notifications/next` every 15-30s. Server returns the
newest un-delivered short message generated by the Memory Engine /QOS
(e.g. from QOS mode transitions already computed server-side — see the
QOS section of the main `README.md`) or an empty response. Simple, fits
the existing request/response API style used throughout `api.ts`, and 15-30s
latency is entirely acceptable for messages like "Coffee time!" — this is
not a real-time chat feature.

Either option requires a new endpoint (`/api/devices/notifications/*`) and
a small "what should this device say next" generator on the server side
that turns QOS state / Memory Engine output into a single short string.
That generator does not exist yet; it is new work, not a refactor of
anything existing.

## 4. The "Copy" button → Log tab (brief item 16)

This is the one piece of the design that maps almost directly onto an
existing, working endpoint:

```
Button press
  → device calls:
      POST https://lot-systems.com/api/logs
      Authorization: Bearer <device token>
      Content-Type: application/json

      {
        "text": "Copy",
        "event": "hardware_copy_signal",
        "metadata": { "device": "lot-node", "deviceId": "<id>" }
      }
  → server creates a Log row exactly as it does for any other log
    (src/server/routes/api.ts:1577, fastify.models.Log.create)
  → row appears in the user's Log tab
```

Required server-side change: add `'hardware_copy_signal'` to the
`displayableEvents` allow-list at `src/server/routes/api.ts:1084` so the
existing `GET /api/logs` handler returns it to the client — a one-line,
additive change, no existing event types touched.

## 5. Weather sensor data path (brief item 14)

Device-read BME280 values are a *second source* for the same concept the
public profile already displays (`Weather` type, `showWeather` privacy
flag in `README.md`). Recommend a new `POST /api/devices/weather` endpoint
that writes into the existing `WeatherResponse`-shaped cache rather than
inventing a parallel weather model — reuses the current cache/read path on
the public profile with no client-side changes needed there.

## 7. Software that connects firmware ↔ LOT API (brief item 10)

For v1, no separate "bridge" server is needed — the ESP32-S3 firmware
talks HTTPS directly to `lot-systems.com` using the endpoints above (device
tokens avoid needing a phone-app intermediary). A phone/desktop companion
app is not required for core operation; the only phone-side moment is
scanning the pairing QR code during first setup (`FIRMWARE.md` §1), which
can be done with the phone's stock camera app since the pairing QR just
encodes a URL.
