DETAIL — src/server/routes/api.ts (`POST /api/story`):
  - Event-filter repair. `recentEntries` was filtering Log rows on
    `event === 'log_entry' || event === 'journal'` — neither value is ever
    written; the real Journal/Log write path stamps `event: 'note'`
    (confirmed against `LogEvent` union in `#shared/types` and every write
    site in api.ts). `selfCareLogs` had the same problem
    (`memory_answer`/`self_care_checkin`/`energy_checkin` vs. the real
    `answer`/`self_care`/`energy_state`/`energy_update` values). Net effect
    before this fix: the AI prompt's "RECENT LOG ENTRIES" and "SELF-CARE
    DATA" blocks rendered as `(none)` for essentially every operator, every
    time — /story was compressing nothing. Both filters now match the
    events the app actually writes.
  - Added `period?: 'day'|'week'|'month'|'year'` to the request body,
    defaulting to `day` (byte-for-byte the old behavior when omitted).
    Widens the log query to `createdAt >= now - N days` and scales the
    per-category sample size (5/10/15/20) and fetch limit (200/500/1500/
    4000) with the window. This is the "day/week/month/year" compression
    S-2 specified in know-how #3 — the same /story pipeline now serves all
    four horizons instead of only ever looking at the last ~10 rows
    regardless of what was asked.
  - Prompt copy updated to name the window and to instruct the model that
    a longer window means denser compression, not a longer story — the cap
    stays under 200 words at every horizon, which is the point.
  - `period` is now persisted on the generated `Log` row's metadata for
    future analytics/debugging.

DETAIL — src/client/components/Logs.tsx (NoteEditor `story-mode` handler,
`/system` help text):
  - Parses an optional trailing window token — `/story week`, `/story
    month`, `/story year`, `/story today` (aliased to `day`) — out of the
    log text before it's sent as `logText`, and passes it through as
    `period`. Bare `/story` is unchanged (defaults to `day`).
  - `/system` help line for `/story` now documents the optional window
    argument instead of describing behavior the endpoint didn't actually
    have.

DETAIL — src/client/queries.ts:
  - `useStoryGeneration` mutation body type gained the optional `period`
    field so the new argument type-checks end to end, client to server.

DETAIL — src/client/utils/logTriggers.ts:
  - Updated the `story-mode` trigger's doc-comment to reflect the
    `[day|week|month|year]` argument. No behavior change — the existing
    `/story` keyword-boundary regex already matches `/story week` etc., so
    detection needed no edit, only the comment was stale.
