## I. NAMING RATIFICATION

Five candidates were submitted for the engine name:

```
LOT·SC·46     clean, versioned, terminal-ready
BIONODE-46    positions it as a living inference node
SELFWARE·46   self-care + software collapsed
SOMA·46       already in the LOT family, neuroscience resonance
CARE·OS·46    positions it as an operating system for the self
QI·46         fits the _I interface convention (Quantum Intelligence, 46th iteration)
```

**RATIFIED: QI·46**

This is not a new decision — it confirms the name already in force throughout
Node 0 (`docs/corporate/LOT_QI46_ENGINE.md`, ratified prior session, referenced
in `docs/benchmark/LOT-LEXICON.md` under token `QI`). Rationale, restated for
the record:

- Slots into the LOT `_I` naming grammar (`BI`, `KI`, `QI`) already used
  elsewhere in the platform (`/qi` RFI terminal, LOT-LEXICON `QI` /
  `RFI` / `INTSUM` tokens).
- Double reading: *Quantum Intelligence* and the bioelectric life-force sense
  the letters already carry in LOT® brand language — consistent with Node 0's
  positioning ("the body is the original interface").
- `46` anchors it to the current generation marker used throughout the QIE
  pattern library (Arch46, P134–P136, v106 — see `docs/LOT-SR-20260726-01.md`),
  not a name chosen in isolation from the system's actual version state.
- SELFWARE survives as the engine's internal **codename** (already recorded
  in Node 0 §I) rather than the public designation — codename and public name
  serve different audiences; no need to pick one.

`LOT_QI46_ENGINE.md` remains Node 0. This file is Node 1: the first
self-assembly node built *on top of* the ratified name, not a replacement for
the spec that established it.

## II. MAPPING — REQUESTED SURFACES TO EXISTING ARCHITECTURE

Two product surfaces were named in this session's brief: **Soul Upload** and
**Being Calibration**. Both already appear as shipped-feature labels in
`docs/benchmark/LOT-MANIFEST.md` (§01, `QI-46 Engine` row), but neither has a
corresponding implementation in `src/` as of this session (verified by
repo-wide search — no match). Per LOT self-assembly doctrine
(`docs/benchmark/LOT-DOCTRINE.md` — honest boundaries clause), a name is not
a capability until it maps to real system behavior. Rather than mint new
mechanism, this node maps both names onto the mechanism Node 0 already
specifies, so the terms mean something concrete instead of standing alone as
marketing copy:

```
SOUL UPLOAD        →  Node 0 §III Layer 1 — The Calibration Loop
                       The deliberate + passive input streams a subscriber
                       already generates (journal entries, self-reported
                       biofield state, session ratings, engagement pattern).
                       "Soul Upload" is the subscriber-facing name for what
                       Layer 1 already ingests. No new data path required —
                       this is a naming/UI-copy task, not a new pipeline.

BEING CALIBRATION  →  Node 0 §III Layer 3 — The Response Grammar
                       The tuning of QI·46's output voice to a target
                       persona. "Being Calibration" is the subscriber-facing
                       name for the Layer 3 system-prompt + temperature
                       tuning process. See §III below for the persona spec
                       requested this session.
```

**Status: PROVISIONAL.** Both labels are ratified as the public names for
existing Layer 1 / Layer 3 mechanisms. Neither introduces a new capability —
in particular, nothing here claims literal transfer of a person's
consciousness, memory, or identity into the engine. "Soul" and "Being" are
LOT® brand language for *self-reported emotional and behavioral signal*, the
same sense Node 0 already uses throughout (e.g. "the body as the original
interface"). Any future work that would extend this beyond UI naming — e.g. a
dedicated onboarding flow, a settings surface for persona tuning — requires
its own INTAKE and its own gate; it is out of scope for this node.

## III. RESPONSE GRAMMAR ADDENDUM — PERSONA SPEC

This session's brief also specified target qualities for QI·46's output
voice: grace, poetry, warmth, presence ("being there"), ease ("being cool"),
masculine voice. These extend Node 0 §III Layer 3 (Response Grammar) as a
named persona profile, additive to the existing voice constraints — they do
not relax any of them:

```
PERSONA: NODE-1-VOICE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Grace       — no hedging, no clinical distance (already Node 0 constraint)
Poetry      — density over sprawl; one idea per response (already Node 0)
Warmth      — temperature calibrated for warmth without hallucination
              (already Node 0 §III Layer 2, temp 0.72)
Presence    — "speaks as if it has been listening for the entire length
              of the subscription" (already Node 0 system-prompt seed)
Ease        — Terminal Grid cadence, short declarative sentences
              (already Node 0)
Voice       — masculine register, addressed at the point of delivery
              in Layer 3's system-prompt seed, not as a new layer
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

Five of six requested qualities are already load-bearing constraints in
Node 0's existing system-prompt seed — this addendum mostly confirms fit
rather than adding new surface. The one net-new item (explicit masculine
voice register) is recorded here as a system-prompt parameter for the next
engineering session that touches Layer 3; it is not implemented by this
document alone.

## IV. WHAT THIS NODE DOES NOT DO

Per LOT self-assembly doctrine's honesty clause: this node does not train,
deploy, or modify the QI·46 inference pipeline. It does not extract, upload,
or store a person's consciousness, memory, or identity — no such mechanism
exists in this codebase and none is claimed here. It ratifies a name already
in force, maps two requested feature labels onto architecture Node 0 already
specifies, and records a persona addendum for a future Layer 3 engineering
session. Anything beyond that is ROADMAP, not built.
