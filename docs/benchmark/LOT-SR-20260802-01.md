FIX LOG (8 fixes, all verified individually against the tsc diff — zero
regressions, only error-count reductions at each step):
  1. QuantumEngineWidgets.tsx — CorrelatedIndexesWidget CARE row read
     `dimensions.selfcare` (typo); real field is `selfCare`. Row rendered
     blank/undefined for every user.
  2. UserMetricsWidget.tsx — CQGS Dashboard "Physiological Profile" view
     called `classifyPhysiologicalCohort()` with 0 of 3 required args.
     Throws at render time (`signals.filter` on undefined) whenever a user
     opens that view — caught by WidgetErrorBoundary, so the view silently
     goes blank rather than crashing the app. Fixed call site + two
     downstream field reads (`.label`->`.archetype`, `.dominant`->
     `.dominantModule`) that referenced properties the function's return
     type has never had.
  3. intentionEngine.ts — two QIE patterns (P95 intent-to-action-gap, P96
     recovery-initiation) set `suggestedTiming: 'active'`, not a member of
     the 4-value urgency enum. `timingWeight['active']` is `undefined`, so
     `confidence * undefined` = NaN, corrupting PatternRecognitionWidget's
     "recommend the optimal module" ranking every time either pattern
     fired. Set both to `'immediate'` (matches their own reason text: "...
     now" / "Support the re-entry").
  4. intentionEngine.ts — `LOG_DEPENDENCY_SOURCES` included `'ecosystem'`,
     a value that has never been a member of `IntentionSignal['source']`
     and that the Car/Home/Computer Connect widgets never actually emit
     (they record under `source: 'intentions'`). Removed the stale entry;
     the physiological-report log-dependency audit was silently including
     a source that can never be observed.
  5. badges.ts — two unrelated badges (Achievement-RPG-v6 "Quarter Drop"
     ○→◉ and Behavioral-v14 "Quarter Drop" ¢·¢) both used id `quarter_drop`.
     Object-literal key collision meant the v6 arcade badge was completely
     unreachable — the v14 definition silently overwrote it at module load.
     Renamed the v6 id to `quarter_drop_first`. (Not yet wired to an
     award-call — see 05c #1.)
  6. shared/types/index.ts + server/models/user.ts + client/queries.ts +
     client/stores/state.ts — `/api/me` (the Portrait/current-user profile
     endpoint every widget reads via `stores.me`) has returned `metadata`,
     `usersTotal`, and `usersOnline` since day one, but the `UserProfile`
     type never declared them. Theme sync, badge sync, and the System-tab
     users-online/users-total counters were all reading through `(user as
     any)` casts or silently-undefined fields with zero compile-time
     protection. Introduced `MeProfile = UserProfile & {metadata,
     usersTotal, usersOnline}`, retyped `getMe()`/`stores.me` to it, and
     removed the two `as any` casts in app.tsx it made unnecessary.
  7. Same investigation surfaced the most severe finding: MonthlyPulseWidget
     (the Month-1-through-12 "portrait deepens" milestone-reveal widget —
     the literal month-to-month UI build-up system this scan was asked to
     check) reads `user.joinedAt`, but `useProfileView()` on the server has
     never selected `joinedAt` into the `/api/me` response. `monthNumber`
     has therefore always computed to `0`, and `if (... || monthNumber < 1)
     return` means the widget has never rendered for any user, for any
     month, since the day it shipped (SR-20260707-01, ~4 weeks ago). Added
     `'joinedAt'` to the server's picked-field list and to the shared
     `UserProfile` type.
  8. Verified fix #6/#7 against the server build in isolation before
     re-running the full gate — an earlier version of the type change
     (adding the 3 fields directly to base `UserProfile`, before splitting
     out `MeProfile`) broke `user.ts`'s `useProfileView(): UserProfile`
     return type. Caught by CHECK B, not shipped.

05c // FINDINGS CATALOGUED, NOT FIXED THIS SESSION
--------------------------------------------------------------------------------
1. quarter_drop_first (fix #5) has no award-call anywhere in the codebase —
   it's now reachable but still never granted. Needs a product decision on
   when "first easter egg of any type" should fire before wiring an
   awardBadge() call.
2. router.ts — the hand-written `Routes` type (`system: void`, `adminUser:
   'userId'`, ...) does not match @nanostores/router's actual `RouterConfig`
   contract (`Record<string, string | Pattern>`; params are derived from the
   path string's `:param` segments, not declared separately). This is a
   compile-time-only hole (already flagged by a `// @ts-ignore FIXME:` on the
   `goTo()` call site) — `router.params.userId` types as `{}` in several
   places (app.tsx DM thread, AdminUser.tsx), so TypeScript cannot catch a
   typo'd param name on the admin or DM routes. Correct fix is to drop the
   custom `Routes` type and let `createRouter(config)` infer params from the
   literal path strings, then adjust `goTo()`'s param-arity handling — touches
   every `goTo()` call site across the app, so deferred as out-of-scope for
   an unattended run.
3. ~90 of the remaining 105 `tsc --noEmit` findings are pre-existing type-
   strictness debt outside the widget-wiring surface this scan targeted:
   AdminUser.tsx/AdminUsers.tsx (admin-only UI), Logs.tsx (several null-vs-
   undefined mismatches), RecipeWidget.tsx/SelfCareMoments.tsx/
   EmotionalCheckIn.tsx (same null-vs-undefined pattern against a shared
   logging helper's signature — likely one shared-signature fix would clear
   3-4 of these at once), sync.ts/Sync.tsx/app.tsx (implicit-any callback
   params), PublicProfile.tsx (reads `.version`/`.streak`/
   `.patternStrengthIndex` off a narrower physiological-report response type
   than the widget expects — same drift class as fix #6/#7, worth a follow-
   up pass), and 25 badges.ts `BadgeType`-category union mismatches (the
   union's 6 categories don't cover 'calendar'/'behavioral'/'achievement'/
   'mastery'/'calendar_easter_egg' used throughout the actual badge table —
   likely the union needs those 5 categories added, mirroring fix #4's
   pattern; deferred as a single well-scoped follow-up rather than a 25-line
   blind edit this run).
