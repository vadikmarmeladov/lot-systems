RECURRING RENDER-PURITY BUG (new finding, fixed this session):
  LOT-SR-20260719-01's R2 fix (System.tsx quantumState useMemo->useEffect)
  addressed one instance of a nanostore .set() write happening synchronously
  during React render — a violation that can block first paint and trigger
  React "update while rendering a different component" warnings when other
  widgets are subscribed to the same store. This session's sweep found the
  SAME bug class recurring in 5 widgets that call recordSignal() (which
  performs intentionEngine.set(...) synchronously) directly in the render
  body, guarded only by a hasRecordedRef ref to fire once per mount:
    - EnergyCapacitor.tsx
    - CohortConnectWidget.tsx
    - GoalJourneyWidget.tsx
    - InterventionsWidget.tsx
    - MicroImageWidget.tsx
  Since all 5 co-mount on System.tsx, initial dashboard load was triggering
  5 synchronous cross-component store writes mid-render, each capable of
  cascading extra re-renders on every other intentionEngine subscriber
  before first paint — a direct contributor to initial dashboard lag.
  FIXED: all 5 moved into React.useEffect (post-paint), preserving identical
  once-per-mount signal semantics via the existing hasRecordedRef guard. Two
  of the five (GoalJourneyWidget, InterventionsWidget) required hoisting the
  effect above their data-loading early-returns to keep hook-call order
  stable across renders (Rules of Hooks) — done by deriving the signal
  payload from a null-safe pre-return value rather than the post-return
  destructured one.

BUNDLE / CODE-SPLITTING (unchanged risk, not fixed — see 06):
