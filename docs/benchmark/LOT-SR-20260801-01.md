05b // WHAT WAS BUILT
--------------------------------------------------------------------------------
ENTRY TIME       Add-entry form gets an optional time input alongside the
                 existing text field. Entries store time + createdAt in
                 calendar_entry metadata (additive — old date-only entries
                 keep working; time is null for them and they behave as
                 all-day, firing at local midnight).
TRACKED WINDOW   New memo buckets entries into "trackedEntries": target time
                 within -5min..+24h of now. Drives both the tick rate (1s
                 while something is tracked, 60s idle pulse otherwise, gated
                 on !document.hidden — same idle-safe pattern as
                 EvolutionMilestoneToast / SystemProgressWidget) and which
                 entries are alert/countdown candidates.
T-MINUS          When the calendar panel is open, a live clock + T-MINUS
                 HH:MM:SS countdown to the nearest upcoming tracked entry
                 renders next to the month header. Plain text, tabular-nums,
                 no icons — consistent with MILITARY PURITY.
ALERT: OVERLAY   New Block ("ALERT:") renders above the widget, always
                 visible (not gated on panel-open), whenever any entry's
                 target time has passed within the last 5 minutes. Uppercase
                 tracking-widest, "DUE <date/time>" — same visual grammar as
                 Logs.tsx's CFG:/ASM:/BIO: blocks.
TODAY: PANEL     New persistent Block listing today's entries regardless of
                 panel state — the "today panel" S-2 asked for. Upcoming-list
                 filter changed from >=today to >today so nothing renders
                 twice between Today: and the upcoming list.
ONE-SHOT LOG     The moment an entry's target crosses into the past, a new
                 'calendar_alert' log fires exactly once — text "[ALERT]
                 TYPE: text — EVENT DUE (...)", metadata {date, time, text,
                 entryType}. Dedup key (date|time|text) is stored in
                 localStorage (capped at 200 keys) so a reload never re-fires
                 an alert already sent, and a React ref guards the same-
                 session double-fire race.
LOGS.TSX         calendar_entry block now shows time inline. New
                 calendar_alert case renders a CAL-ALERT: block: "EVENT DUE —
                 TYPE", the entry text, then date/time — same field-manual
                 voice as every other military handler in the file.
CALENDAR_UPDATE  recordCalendarUpdateSignal() added to intentionEngine.ts and
                 wired to fire alongside the alert log. This closes a real,
                 pre-existing gap: Pattern 46 (temporal-coherence-window) has
                 checked `signal === 'calendar_entry' || signal ===
                 'calendar_update'` since it was written, and
                 WIDGET_DEPENDENCY_MAP has mapped 'calendar_update' -> module
                 'calendar' since the same commit — but nothing ever emitted
                 it. It is now emitted at the one moment that semantically
                 matches its name: when a scheduled entry goes live.
WHITELIST        'calendar_alert' added to the server displayableEvents
                 array (routes/api.ts) in the same commit as the writer, not
                 after the fact — see Backend Whitelist Hygiene below.
