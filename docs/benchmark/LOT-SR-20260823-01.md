05 // FEATURE — LOT MAIL
--------------------------------------------------------------------------------
TRIGGER      /email (or /mail) to <Name> typed in a Log entry opens an inline
             compose Block (✉️ LOT MAIL) without leaving the Log editor —
             extends logTriggers.ts RULES (additive, no store coupling) and
             Logs.tsx's existing trigger-effect chain, same shape as /prayer,
             /qi, /story.
RESOLVE      Name -> user via new POST /api/users/search (firstName/lastName
             ILIKE + CONCAT match, limit 8, self-excluded). Simplest-possible:
             takes the top match, no disambiguation UI.
SEND         Reuses the pre-existing (but previously non-functional, see BUGS)
             DirectMessage model/routes — no new send path.
SYNC INBOX   New GET /api/direct-messages returns latest message per thread
             partner (dedup in JS over a 300-row recent scan, capped 20
             threads). Rendered as a "✉️ LOT Mail" list at the top of Sync.tsx,
             each row -> stores.goTo('dm', {userId}) -> the DirectMessageThread
             component, which was already fully built and router-wired
             (/dm/:userId) but had zero call sites anywhere in the app before
             this session.
LIVE UPDATE  Sync.tsx now also listens for the 'direct_message' SSE event and
             refetches the inbox — dead until the relay fix below.
COHORT LINK  CohortConnectWidget's "Send message" on a cohort match now calls
             stores.goTo('dm', {userId}) directly instead of a bare
             goTo('sync') that dropped which user was clicked. This is the
             LOT Community / Cohort Dating integration point requested — no
             separate "Cohort Dating" surface exists yet, so the connection is
             at the one place cohort matches already surface a person.

05b // BUGS FOUND + FIXED (pre-existing, blocking)
--------------------------------------------------------------------------------
BUG 1  No migration ever created the `direct_messages` table. The model and
       both /direct-messages routes existed and would throw "relation does
       not exist" on first use. Added
       migrations/20260823120000_add-direct-messages-table.cjs, structure
       copied from the chat_messages_likes migration (same UUID pk shape).
BUG 2  The /sync SSE relay's event switch (api.ts ~L359-389) had no case for
       'direct_message' — sync.emit('direct_message', ...) fired into the
       in-process emitter but the switch silently dropped it before it ever
       reached the wire. DirectMessageThread.tsx's live listener was dead
       code in production. Added a case, gated to
       data.senderId/receiverId === req.user.id so a thread only relays to
       its two parties (chat_message_like does the equivalent per-viewer gate
       for isLiked).
       This is the SAME failure class DOCTRINE already names for formatLog()
       (SR-20260630-01: "any event type that must influence X needs an
       explicit case, else silent, unerrored disappearance") — now confirmed
       in a second dispatch site (the SSE switch, not just formatLog). Worth
       folding as a general clause once a third instance appears.
