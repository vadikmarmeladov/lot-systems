## CALENDAR v12 — DESIGN NOTES

### Entry Type Visual System
Each entry type has a fixed single-character prefix:
- `·` note — ambient, informational
- `▸` task — action-required, directional
- `◉` call — high-engagement, point of contact

Used in: upcoming entries list, selected-date entries panel.

### Time-Aware Scheduling
Time field is optional `<input type="time">` alongside the text field. When set:
- Stored as `metadata.time` (HH:MM string)
- Shown in upcoming list after the date
- Triggers precision alert windows: T-60, T-30, NOW

When not set:
- Entry fires a single TODAY alert when the date arrives

### Military-Grade Alert Format
```
◈ SCHEDULE ALERT ◈
[TASK]
Sprint Review — 14:00
FRI, JUNE 27, 2026
T-30MIN
```

Alert is simultaneously:
1. Displayed as fixed-position toast (top-right, 9s)
2. Written to Log as `calendar_alert` event with full metadata

### Delete Flow
- Group-hover `×` on selected-date entry panel
- Calls `DELETE /api/logs/:id` — server enforces `calendar_entry` event type only
- On success: refetches `/api/logs` query, entry disappears from all views

## DOCTRINE UPDATE

**Temporal Alert Protocol (TAP):**
All time-sensitive schedule entries must propagate through the Log. Every alert fired is a permanent record — the system maintains a full history of what was surfaced, when, and at what countdown. This creates an audit trail for schedule integrity.

**Notification Dedup Invariant:**
Alert keys are stored as `{logId}:{alertType}` in localStorage. A given alert fires exactly once per window, even across sessions. The ring buffer caps at 2000 entries to prevent unbounded growth.
