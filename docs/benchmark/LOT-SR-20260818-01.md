05 // ROUTINES IMPLEMENTED (this session)
--------------------------------------------------------------------------------
R1 LOG COMMAND       Added `lot-email` to LogTrigger + RULES in
                     logTriggers.ts (keyword `email`, no emoji collision —
                     ✉️ reserved as future shorthand). Whole-token /email
                     regex reused unchanged from the existing detector.
R2 COMMAND PARSING   Logs.tsx: `/email to <name>` regex extracts the
                     recipient's first name; remaining log text (command
                     stripped) becomes the message body. Empty body falls
                     back to a default greeting rather than blocking send —
                     mirrors the /prayer, /story trigger UX (loading state,
                     inline result Block, same Arial/opacity-60 styling).
R3 LOT COMMUNITY     Recipient resolution = case-insensitive firstName
                     lookup against the full registered Users table. This
                     *is* the "LOT Community" directory in its simplest,
                     honest form — every registered member is a Community
                     member. No new UI surface was built for this; it is
                     the resolver behind the /email command.
R4 COHORT DATING     Reused the EXISTING cohort-matching engine
                     (findCohortMatches in #server/utils/patterns, already
                     serving GET /api/cohorts) rather than inventing new
                     matching logic. On send, sender vs. resolved recipient
                     is checked as a single-candidate cohort match
                     (location + archetype + pattern overlap scoring,
                     unchanged formula). A match is called out inline in
                     both the Sync post ("❤️ COHORT MATCH") and the email
                     body itself. Best-effort — wrapped in try/catch, never
                     blocks the send if a user has too few logs to profile.
R5 PERSISTENCE       New `lot_emails` table + LotEmail Sequelize model
                     (senderId, recipientId nullable, recipientNameRaw,
                     message, isCohortMatch, delivered) — the actual "LOT
                     Email system" of record, distinct from a one-off chat
                     string. Migration is additive-only (new table, no
                     touched columns) — safe to run any time via
                     `npm run migrations:up`.
R6 REAL EMAIL SEND   New #server/utils/lot-email.ts — sendLotEmail() via
                     the existing Resend client pattern (same `from:
                     auth@lot-systems.com` used by verification email).
                     Fires only when the resolved recipient has a
                     registered address; failure is caught and logged,
                     never blocks the Sync post or Log entry.
R7 SYNC INTEGRATION  Deliberately reused the EXISTING chat_messages table
                     + `chat_message` SSE event instead of adding a new
                     Sync event type or touching Sync.tsx. The /email
                     command posts a formatted line ("✉️ LOT Email ->
                     <name>[ ❤️ COHORT MATCH]: <message>") through the same
                     path POST /api/chat-messages already uses. Result: a
                     composed /email message appears in Sync immediately
                     (SSE) and persists across refresh (GET /api/chat-
                     messages) with ZERO client-side Sync changes and zero
                     new SSE plumbing — this is the "simplest" system
                     honored literally.
R8 AUDIT TRAIL       Log.create({ event: 'lot_email_sent', ... }) on every
                     send, matching the existing direct_message_sent /
                     chat_message conventions (getLogContext + metadata).
R9 API               POST /api/lot-email — auth required, suspended-user
                     block, same canAccessChat gate (Usership/Onyx/Legacy/
                     RND/Admin) as Sync itself, rate-limited 10/min.

05a // DESIGN DECISIONS / SCOPE HELD DELIBERATELY SIMPLE
--------------------------------------------------------------------------------
- No new "LOT Community" page/route was built. The directory IS the Users
  table; a dedicated browsable Community UI is a natural next step but was
  out of scope for "simplest."
- No swipe/match UI for Cohort Dating. The existing /api/cohorts matching
  formula is consumed, not reinvented, and surfaced only as an inline tag
  on LOT Email sends. A dedicated Cohort Dating surface is future work.
- Recipient resolution is exact (case-insensitive) firstName match, not
  fuzzy. Ambiguous/duplicate first names resolve to whichever Sequelize
  returns first — acceptable for a v1, flagged here for S-2 awareness.
- `lot_emails` migration was written and typechecked but NOT run against
  a live database from this session (no DB reachable in this container).
  Runs automatically on next `npm run migrations:up` / `production:run`.

08 // HOW TO USE
--------------------------------------------------------------------------------
In Log, type:  /email to Hitomi. <optional message>
- If "Hitomi" matches a registered user's first name, a real email is sent
  to her registered address (if present), the send is tagged as a Cohort
  Match when the existing matching engine agrees, and a line appears in
  Sync immediately: "✉️ LOT Email -> Hitomi[ ❤️ COHORT MATCH]: <message>"
- If no match is found, the Sync line still posts (marked "not in LOT
  Community") but no email is sent.
- /system now lists "/email to X" alongside the other Log commands.
