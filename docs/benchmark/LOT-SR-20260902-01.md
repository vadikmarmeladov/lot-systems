WHAT CHANGED AND WHY
--------------------------------------------------------------------------------
Both /system and /story existed before this session (logTriggers.ts already
enumerated 'system-help' and 'story-mode' triggers; Logs.tsx already dispatched
them; POST /story already called Together AI). Two concrete gaps against the
stated spec were closed rather than re-implementing from scratch:

1. /story HAD NO PERIOD. It always summarized "recent data" (last 200 logs,
   no explicit window) regardless of what the operator typed after /story.
   The spec asks for "a compressed story of your day/week/month/year." Added:
   - parseStoryPeriod() in logTriggers.ts — pure regex parse of
     /story (day|week|month|year), default 'day'.
   - Logs.tsx story-mode handler now parses the period, strips it from the
     persisted log text, and passes it to submitStory(); a storyPeriod state
     labels the rendered story block (e.g. "📖 MONTH").
   - useStoryGeneration (queries.ts) request type gained an optional `period`.
   - POST /story (api.ts) now resolves period -> {window, sampleLimit,
     wordTarget, noun} (day=24h/200 logs/100-200w, week=7d/500/150-250w,
     month=30d/1000/200-300w, year=365d/2000/250-350w), filters Log rows by
     `createdAt: { [Op.gte]: windowStart }` (Op already imported, consistent
     with existing date-window queries elsewhere in the file), and adjusts the
     system prompt to ask for an arc-level summary on longer windows instead of
     the day-level "quiet truth" closer. Generated stories now persist `period`
     and `signalCount` in their Log metadata so future compressions can see
     what was already compressed.

2. /system COULD DRIFT FROM WHAT DETECTION ACTUALLY RECOGNIZES. The help text
   was a hand-maintained string array in Logs.tsx, entirely separate from the
   RULES array in logTriggers.ts that drives detectTriggers(). A command added
   to one and forgotten in the other would fail silently — no build error, no
   runtime error, just a wrong help screen. Added `command`/`describe` fields
   to TriggerRule and a getSystemHelpLines() export; Logs.tsx's system-help
   handler now renders from that single source instead of its own list. A rule
   with no `describe` (❗ cohort-support, /sil) stays a hidden trigger by
   design — omitted from /system on purpose, not by oversight.

Also written: docs/technical/LOG-COMMAND-SYSTEM.md — a from-scratch technical
reference for the whole Log/Journal command system (design premise, context-
snapshot-on-click, the passive-AI/no-prompts Log philosophy, full command
table generated from RULES, the /story compression pipeline end-to-end
including the LOT User data -> Quantum Intent Engine -> Together AI ->
personalized-data hop, an Arcade/gamification section addressing S-2's note
on the badge system as this self-care company's arcade layer, and an honest
"Known Duplication" section flagging the two independent composeLocalStory()
implementations (memory.ts vs memory/story-generator.ts — both live, used by
different routes, not collapsed in this pass since that touches a public API
route and deserves its own green-gated benchmark).

No badge/gamification code was added this pass. The doc names the natural next
increment (a badge on first /story year, etc.) explicitly as future work
rather than reaching into a 7,500-line file with pre-existing duplicate-key
warnings under a single benchmark cycle — see Cardinal Rule 1 (no red pushes)
and honest-boundaries guidance on judgment vs. mechanism.
