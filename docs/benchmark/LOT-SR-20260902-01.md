## What changed, in plain terms

The Calendar widget (`CalendarWidget.tsx`) already let you pin a note, task,
or call to a date and log it. This session added two things the directive
asked for by name: **time tracking** and **military-grade notifications**,
without touching the minimalist visual language already in place.

### Time tracking

Each entry under a selected date now has a small `▶ Track` control. Clicking
it engages a clock (`[OPS] TIMER ENGAGED`) and logs a `calendar_timer_start`
event carrying the entry's id, date, text, and type. Clicking again secures
it (`[OPS] TIMER SECURED`), logging `calendar_timer_stop` with the elapsed
duration. Only one clock runs at a time — starting a second entry's timer
first auto-secures whatever was running, so no segment is ever silently
dropped. The active timer is persisted to `localStorage`
(`lot_calendar_active_timer`) and rehydrated on load, so it survives a
closed widget, a page reload, or a new tab — the clock is a fact about the
entry, not about whether the panel happens to be open. Total tracked time
per entry is derived on the fly by summing every `calendar_timer_stop` log
matching that entry's id, so the number shown is always a projection of the
Log, never a second source of truth that can drift from it.

### Military-grade ops-log notifications

A new `CalendarOpsToast` component renders a bottom-right corner
notification for every calendar event that matters: timer engaged, timer
secured, an entry filed, or a once-per-day SITREP naming how many items are
due today. Each toast carries a bracketed ops code and a Zulu timestamp —
`[OPS // TIMER ENGAGED] 14:32:07Z` — styled with the same accent-color,
grid-fill, border-only language every other widget in this codebase already
uses, so "military-grade" reads as *terse and coded*, not as a new visual
language bolted onto a minimalist UI. It auto-dismisses after five seconds,
matching the existing `EvolutionMilestoneToast` pattern it was modeled on.
Events are delivered through a tiny nanostore atom (`$calendarOpsEvent`) in
the new `calendarOps.ts` store, so any future widget can push its own ops
line through the same toast without CalendarWidget knowing about it.

### Why a new store file

Keeping the timer's persisted state and the toast's event bus in
`calendarOps.ts` (rather than inline in the widget) means the running timer
survives even if `CalendarWidget` unmounts, and keeps `CalendarWidget.tsx`
focused on rendering rather than on localStorage bookkeeping.

### Reliability notes

- Timer identity is keyed by the entry's underlying Log `id`, not by
  date+text string matching — so two entries with identical text on the
  same day never collide.
- `localStorage` reads/writes are wrapped in `try/catch` everywhere (timer
  persistence, SITREP dedupe) so private-mode or quota failures degrade to
  in-memory behavior instead of throwing.
- The SITREP due-today check fires at most once per calendar day per
  browser (deduped via a stored date string), so reopening the app doesn't
  re-alert on the same items.
