05 // UNDERSTANDING — WHAT THE ASTROLOGY BLOCK ACTUALLY IS
--------------------------------------------------------------------------------
Ambient, not personal. shared/utils/astrology.ts computes four real,
reproducible readings from the clock: hourly Japanese zodiac (2h windows),
Western zodiac (calendar date), moon phase + illumination (synodic-month
calc from a known 2000 new moon), and rokuyo (6-day cycle from a known 2000
Sensho anchor). None of these read the user's birth data — the code comment
is explicit: "not a personal natal chart." This is deliberate and correct;
this session preserved that honesty and added personalization the other
way — from the user's own behavior, not invented astrology.

Three real surfaces already existed and, before this session, disagreed
with each other:
  1. System.tsx "Astrology:" block — computes the live reading every 15 min
     (tab-visibility gated) and displays it; also fires recordAstrologySignal
     into the QIE bus once per calendar day so Tier-1 widgets (system,
     cosmic per WIDGET_DEPENDENCY_MAP) can key off it.
  2. server/utils/logs.ts getLogContext() — stamps astroRokuyo/astroMoonPhase/
     astroMoonIllumination/astroHourlyZodiac/astroWesternZodiac onto the
     `context` field of nearly every Log row at write time (used by ~20 call
     sites in api.ts + memory.ts), in the user's own saved timeZone.
  3. Logs.tsx — reads that stamped context, but only rendered it inline for
     one event type (system_snapshot); QuantumSignWidget's "New Patches" ->
     Astrology view showed a *separate*, fabricated astrology-flavored patch
     name (Lunar Reset / Solar Return / Mercury Direct / Venus Transit)
     rotated by day-of-year — a number with no relationship to the real
     rokuyo/moon-phase reading computed in (1) and (2).

05a // FEATURES SHIPPED THIS SESSION
--------------------------------------------------------------------------------
F1 PERSONAL AFFINITY   New getAstrologyAffinity(logs, minSamples=5) in
                       astrology.ts: tallies each user's own logged
                       astroRokuyo history and returns their most-frequent
                       rokuyo day + count/total. Real per-user statistic
                       computed from data already on disk — not a generated
                       reading, not numerology. Gated on >=5 samples so a
                       new user's first day doesn't read as "a pattern."
                       Wired into both System.tsx Astrology block layouts
                       (compact + full pro) as a second line: "Your rhythm:
                       most active on <rokuyo> days (N/total)" — shown only
                       once the user has enough history.

F2 WIDGET SYNC          QuantumSignWidget's Astrology patch selector now
                       reads the SAME getRokuyo()/getMoonPhase() functions
                       System.tsx uses, indexing the 4 patch names by the
                       real 6-value rokuyo cycle instead of an unrelated
                       365-value day-of-year rotation. The patch description
                       now appends the live rokuyo + moon phase + illumination
                       so the two "Astrology:" surfaces in the app (System
                       dashboard, Quantum Sign patches) can no longer
                       disagree — they're driven by one function pair.

F3 LOGS SYNC            LogContainer (Logs.tsx, the shared wrapper every one
                       of the ~90 log-event render branches passes through)
                       now includes the stamped astroRokuyo/astroMoonPhase
                       in its hover-reveal context line for ANY log entry
                       that carries it — previously only the system_snapshot
                       branch surfaced it inline. Server already stamps this
                       on ~20 log-writing call sites (mood, journal, answer,
                       plan_set, etc.); the UI just wasn't reading it except
                       in one place. One shared edit, not ~90 per-branch
                       edits — avoids duplicating the same fix across every
                       event-type render case.
