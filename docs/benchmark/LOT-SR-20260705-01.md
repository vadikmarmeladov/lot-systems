06 // HARDWARE DESIGN SUMMARY
--------------------------------------------------------------------------------
PRODUCT:      COSMO® Cube — Model S1 "Signal Tile". First physical SKU in the
              COSMO® hardware line — smaller and nearer-term than the soul-
              transfer robot in docs/corporate/LOT_ROBOTICS_COSMO.md, and the
              hardware realization of the "physical extension" arc already
              described in docs/corporate/LOT-CUBIQ-OPERATOR.md §04/§07.

FORM FACTOR:  40mm x 40mm, two-piece CNC 316L stainless steel body. Face A
              mirror-polished (laser-etched mark + ceramic Qi charging
              window). Face B bead-blasted, holds camera + e-paper screen +
              Copy button.

KEY ENGINEERING CALL:   the briefed 5mm height is flagged as an open risk,
              not silently accepted or silently downgraded — two configs
              defined (CONFIG A 5mm/specialty parts, CONFIG B 8mm/all-stock
              parts) sharing a board-footprint family, with the Phase 1
              prototype run as the explicit decision gate
              (LOT-COSMO-CUBE-HARDWARE-SPEC.md §03,
              LOT-COSMO-CUBE-ROADMAP.md §03).

KEY ENGINEERING CALL:   Qi wireless charging cannot couple through solid
              stainless steel (eddy-current loss) — resolved with a ceramic
              charging window inset into Face A, the same approach used by
              metal-backed smartwatches (LOT-COSMO-CUBE-HARDWARE-SPEC.md §04).

FIRMWARE:     ESP32-S3-class MCU (WiFi+BLE+camera-capable), deep-sleep/poll
              loop (90s default) rather than a persistent socket, on-device
              session compression before any sync — explicitly modeled on
              this repo's own Async Signal Recording and QIE
              sync-every-10-signals doctrine (LOT-DOCTRINE.md) rather than
              inventing a new principle.

API BRIDGE:   New Device + DeviceCode models (mirror the existing
              email-code.ts pattern), new device-api.ts route file (sixth
              route module alongside api.ts/admin-api.ts/os-api.ts/
              public-api.ts/auth.ts), POST /api/device/copy writing to the
              same Log model as POST /logs (src/server/routes/api.ts:1455).
              Explicitly flags the displayableEvents whitelist addition
              ('device_copy') as required — citing Backend Whitelist
              Hygiene and the exact prior incident it exists for
              (SR-20260604-01).

PAGER LINE:   AI-authored ambient text reuses the existing Memory Engine's
              Claude Haiku tier rather than a new inference path; explicitly
              reconciled against the site's own stated "no push, no alert,
              no interruption" doctrine (About.tsx Context Over Notification)
              — the physical object is a deliberately separate channel from
              the browser client, which keeps its no-push posture unchanged.

ROADMAP:      5 phases, design-freeze → prototype → API/pilot → CNC tooling →
              100-unit run, ~5-6 months, ~$6.5K-$16.8K all-in program cost
              depending on config, PCBWay used for PCB fab + SMT + CNC
              stainless enclosure under one vendor. Risk register covers
              certification posture for a radio device sold to end users
              (recommend pilot/beta framing for the 100-unit batch rather
              than general retail, standard early-hardware practice).

MANUAL:       Markdown source + pdfkit-generated 4-page PDF (verified valid
