09 // DESIGN NOTES (for S-2 — not part of the fixed template, kept because
    the directive's four requirements deserve a straight account of what
    was actually built and what was deliberately left out)

WHAT WAS BUILT
  - Log: typing "/email to <name>" anywhere in a log entry fires a new
    'email-send' trigger (logTriggers.ts). The name is read up to the next
    line break or punctuation; whatever text remains in the log (command
    stripped) becomes the email body, falling back to a timestamped default
    if the log is otherwise empty. Documented in the /system help screen.
  - Server: POST /api/emails (api.ts) — same access gate as Chat
    (Usership/Onyx/Legacy/R&D/Admin), same dual-write as chat_message
    (creates an `Email` row, then a Log row with event:'email' for the
    permanent record), same broadcast (sync.emit('email_sent', ...)) added
    as a new case in the /sync SSE switch.
  - Sync: Sync.tsx subscribes to 'email_sent' and appends a synthetic item
    into the same live-feed array the chat messages use — an Email renders
    inline in Sync as "✉️ to <name> [· LOT Community] — <body>", using the
    existing render loop with no new UI surface. Click-to-like is guarded
    off for these synthetic rows (isEmail flag) since there is no
    ChatMessage row behind them to like.
  - LOT Community / Cohort Dating: added LOT_COMMUNITY_PERSONAS, a small
    named registry in shared/constants (seeded with "hitomi"). A recipient
    name matching the registry is tagged channel:'community' instead of
    'direct' and rendered with a "· LOT Community" tag. That is the entire
    touchpoint — no matching engine, no profiles, no mutual opt-in.

WHAT WAS DELIBERATELY NOT BUILT (simplest, and honestly scoped)
  - No recipientUserId / real-user resolution. The recipient is a free-text
    name. Matching it against real User rows was considered and dropped —
    first-name matching is ambiguous (duplicate names) and privacy-loaded,
    and nothing in the directive asked for delivery to an existing account;
    "email a name that may not be a member yet" is the actual point of
    difference from the existing DirectMessage/Chat, which require a real
    receiverId.
  - No persisted Email history feed / pagination. Sync shows emails only
    as they arrive live (SSE), same as it already did for chat before this
    session for anything not in the initial fetch. The durable record is
    the Email table row plus its mirrored Log entry (visible in the Log
    history view via a new 'MAIL:' block) — not a separate inbox UI.
  - No Cohort Dating matching/swipe/profile system. That would be a real,
    multi-week feature (profiles, mutual consent, safety review) and
    building a stub of it to satisfy a keyword would be dishonest scope
    inflation. The persona registry is the smallest real integration point
    a future Cohort Dating feature could hang off of.
