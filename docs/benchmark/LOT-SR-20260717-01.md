WHAT WAS BUILT (verbatim, for the record):
  - CalendarEntry now carries id (source Log id), time (HH:mm), durationMinutes,
    remindMinutesBefore, sourced straight from calendar_entry Log metadata — no
    new DB migration; Log.metadata is already a free-form JSON column.
  - Add-entry form gained an optional time input plus (only once a time is set)
    a duration-in-minutes field and a remind-lead select (off/5/15/30/60,
    default 15) — stays hidden/out of the way for plain date+note entries, so
    the minimalist UI is unchanged for the common case.
  - A polling effect (20s tick, 5-minute catch-up window) computes up to three
    stages per timed entry: `reminder` (T-minus lead), `start` (T-0), `end`
    (duration elapsed) — this is the actual time-tracking: entries aren't just
    a date+text pair anymore, they have a lifecycle.
  - Each due stage both (a) creates a `calendar_alert` Log row — metadata:
    sourceLogId, stage, date, time, entryType, text, durationMinutes,
    remindMinutesBefore — and (b) queues a toast. Dedup is keyed off persisted
    Log rows (`sourceLogId|stage`), not localStorage, so it survives reloads
    and won't double-fire across remounts; a same-tick in-memory ref guards the
    gap before the create-log round-trip lands.
  - The toast ("Calendar Ops" / stage headline / entry type+time / entry text)
    is monospace, uppercase-label, grid-fill-bordered — same visual family as
    EvolutionMilestoneToast but its own keyframes (calendarOpsFadeInUp/Out) so
    it has no load-order dependency on that component; positioned
    bottom-right to avoid colliding with Evolution's bottom-center toast.

KNOWN LIMITATION (disclosed per doctrine's honesty clause, not hidden):
  This is client-side, tab-must-be-open scheduling — there is no service
  worker, push subscription, or server cron backing it (scheduled-jobs.ts has
  no calendar-alert job; confirmed by reading it before writing this). If the
  tab is closed through an entire trigger window, that alert is skipped, not
  queued. "Reliable" here means: no duplicate fires, no stale-entry spam on
  reopen, and correct within its 5-minute window while the app is open — not
  guaranteed delivery while offline. A real push-notification path would need
  a server-side job plus browser Notification permission flow; out of scope
  for this session, flagged for a future one.
