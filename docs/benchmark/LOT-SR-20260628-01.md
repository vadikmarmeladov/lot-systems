## 1. SCOPE

Investigation of all button lagging and rendering performance problems across the
LOT-Computer client: event handler blocking, CSS repaint triggers, React re-render
cascades, and store subscription overhead. Covers commit history from June 2026
to present (HEAD: 1271cd3).

---

## 2. RESOLVED ISSUES (HISTORICAL)

### 2.1 Button Hover Lag — CSS `background-image` Transition
**Commit:** `2c0da2f` · Jun 12, 2026  
**Root cause:** `.grid-fill-hover` was transitioning `background-image` (two
`linear-gradient()` calls resolved from CSS custom properties). Browsers cannot
GPU-accelerate this property — every hover fired a full CPU repaint across all
20+ interactive elements simultaneously.  
**Fix:** Replaced with a `::before` pseudo-element. The grid pattern is pre-rendered
once; hover toggles `opacity` only (GPU-composited, zero repaint cost). Transition
reduced to `180ms ease` for a breeze-like feel.  
**Files:** `src/client/index.css`  
**Status:** CLOSED

### 2.2 Tab Label Movement on Hover
**Commit:** `1271cd3` · Jun 27, 2026  
**Root cause:** The GPU compositor layer for `grid-fill-hover::before` was not
pre-promoted. The browser promoted it at the moment of the first hover, causing a
sub-pixel text shift on all tab labels when `opacity` started transitioning.  
**Fix:** Added `will-change: opacity` to `grid-fill-hover::before` — layer is
promoted at page load, eliminating the shift entirely.  
**Files:** `src/client/index.css`  
**Status:** CLOSED

### 2.3 Memory Button Lag — Synchronous `recordSignal()`
**Commit:** `78745c3` · Jun 21, 2026  
**Root cause:** `MemoryWidget`'s `onAnswer` click handler called `recordSignal()`
synchronously. This ran localStorage reads/writes and the full intention-pattern
analysis before React had a chance to commit visual feedback. The button appeared
to freeze for 20–80ms on tap.  
**Fix:** Deferred `recordSignal()` with `setTimeout(0)` — React commits the visual
state change (button highlight, cascade fade) before the heavy synchronous work
runs.  
**Files:** `src/client/components/MemoryWidget.tsx`  
**Status:** CLOSED

### 2.4 Tab Switching Lag — All TabPanels Subscribing to `stores.router`
**Commit:** `ad37d19` · Jun 23, 2026 (reinforced in `b68e842`, `1271cd3`)  
**Root cause:** All five `TabPanel` instances subscribed individually to
`stores.router`, so every tab navigation caused a full re-render of every panel —
including the heavy `System` component (14+ store subscriptions, 40+ widgets).  
**Fix:** Router subscription consolidated into a single `TabPanels` wrapper.
`TabPanel` made into a `React.memo` component with a custom comparator
(`(prev, next) => prev.active === next.active`) — only the two panels whose
`active` prop changed (old → false, new → true) re-render on navigation.  
**Files:** `src/client/entries/app.tsx`  
**Status:** CLOSED

### 2.5 Button.tsx Global Store Subscription — All Buttons Re-rendering on Theme/Mirror Toggle
**Commit:** `4d48dfb` · Jun 3, 2026  
**Root cause:** `Button.tsx` subscribed to both `stores.theme` and
`stores.isMirrorOn` regardless of `kind` prop. Every theme change or mirror toggle
re-rendered every button instance in the UI.  
**Fix:** Split into three path-specific sub-components:
- `PrimaryBtn` — subscribes to `stores.theme` only
- `SecondaryRoundedBtn` — subscribes to `stores.isMirrorOn` only
- `secondary` (default) — zero store subscriptions  
**Files:** `src/client/components/ui/Button.tsx`  
**Status:** CLOSED

### 2.6 Tab Component Re-render Cascade — Logs, System, Sync, Settings Without Memo
**Commit:** `1271cd3` · Jun 27, 2026  
**Root cause:** `Logs`, `System`, `Sync`, `Settings` — each a large component tree —
had no `React.memo` wrapper. Every `TabPanels` re-render (triggered by router store
changes) forced a full reconcile of whichever tab was active.  
**Fix:** Wrapped all four components in `React.memo(function ComponentNameInner())`.
Since these components take no external props (reading everything from stores
directly), React skips reconcile unless a store they subscribe to actually changes.  
**Files:** `src/client/components/Logs.tsx`, `System.tsx`, `Sync.tsx`, `Settings.tsx`  
**Status:** CLOSED

## 3. ACTIVE ISSUES

### 3.1 `.grid-fill` (Static Variant) Still Transitions `background-image`
**Severity:** MEDIUM  
**File:** `src/client/index.css:98–99`  
**Affected components:** `PlannerWidget.tsx` (4 occurrences, lines 161, 183, 205, 227),
`SystemProgressWidget.tsx` (1 occurrence)

The June 12 fix correctly replaced the hover transition on `.grid-fill-hover` with a
GPU-composited `opacity` approach. However, the static `.grid-fill` class (used for
_always-visible_ filled states, such as active Planner blocks and the active
SystemProgress item) was not updated:

```css
/* index.css:93–100 — CURRENT (unfixed) */
.grid-fill {
  background-image: ...;
  background-size: var(--evolution-grid-size) var(--evolution-grid-size);
  transition: background-size var(--evolution-transition-speed) ease,
              background-image var(--evolution-transition-speed) ease;  /* ← non-GPU */
}
```

When the theme accent color changes (`--acc-color-400`) or the grid opacity evolves
(`--evolution-grid-opacity`), every element carrying `.grid-fill` triggers a full CPU
repaint at the transition frame rate (400ms default). PlannerWidget renders up to 4
of these simultaneously. This is the same root cause as SR-2c0da2f.

**Recommended fix:**

```css
.grid-fill {
  position: relative;
  isolation: isolate;
}

.grid-fill::before {
  content: "";
  position: absolute;
  inset: 0;
  z-index: -1;
  background-image:
    linear-gradient(to right, rgb(var(--acc-color-400) / var(--evolution-grid-opacity)) 1px, transparent 1px),
    linear-gradient(to bottom, rgb(var(--acc-color-400) / var(--evolution-grid-opacity)) 1px, transparent 1px);
  background-size: var(--evolution-grid-size) var(--evolution-grid-size);
  border-radius: inherit;
  pointer-events: none;
  will-change: opacity;
  transition: opacity var(--evolution-transition-speed) ease;
}
```

Remove the `background-image` and `background-size` properties from `.grid-fill` itself.
The pseudo-element carries the grid; its `opacity` is GPU-composited. Accent/opacity
changes animate via opacity rather than recomputing the gradient on every frame.

### 3.2 MemoryWidget — Deeply Nested `setTimeout` State Machine
**Severity:** LOW–MEDIUM  
**File:** `src/client/components/MemoryWidget.tsx:75–101` and `:195–230`

The post-answer animation sequence uses 4–5 nested `setTimeout` calls to drive state
transitions:

```
setTimeout 1500ms → setQuestion(null) → setResponse()
  └─ setTimeout 100ms → setIsResponseShown(true)
       └─ setTimeout 6000–8000ms → setIsShown(false)
            └─ setTimeout 1500ms → setIsDisplayed(false)
```

This pattern works but cannot be cancelled mid-sequence (no cleanup in `useEffect`).
If the user navigates away or the widget unmounts between timeouts, stale state
setters fire on an unmounted component. While React 18 silences the warning, the
underlying state updates still queue, potentially interfering with re-mount state.

**Recommended fix:** Collect all timeout IDs and cancel them in a `useEffect` cleanup.

### 3.3 MemoryWidget — `createMemory` Triggers `queryClient.invalidateQueries` on Success
**Severity:** LOW  
**File:** `src/client/components/MemoryWidget.tsx:65–72`

On answer submission, `createMemory` immediately fires an API mutation. Its `onSuccess`
handler calls `queryClient.invalidateQueries(['/api/memory', date])`. This invalidation
causes React Query to re-fetch and then re-render the component tree consuming that
query. If the widget is in the middle of its animation sequence (see 3.2), the re-fetch
could race with the animation state. Not a hard bug today but a fragility point.

## 6. SUMMARY

The core button and rendering lag issues were systematically diagnosed and fixed over
the period June 3–27, 2026, across three root-cause categories:

- **CSS non-GPU transitions** → fixed for `.grid-fill-hover`; `.grid-fill` still pending
- **Synchronous click-handler work** → fixed in MemoryWidget via `setTimeout(0)`
- **React re-render cascades** → fixed via `React.memo`, subscription minimization,
  and `TabPanel` consolidation

The system is significantly more responsive post-fixes. One confirmed regression
surface remains: `.grid-fill` (static filled state in Planner and SystemProgress) still
uses a `background-image` transition. This should be the next fix before closing this
investigation.
