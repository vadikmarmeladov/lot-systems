05 // DESIGN
--------------------------------------------------------------------------------
COMPOSE   Log entry doubles as the mail body — write normally, then append
          "/email to <Name>" anywhere in the entry. parseEmailTrigger() strips
          the trigger phrase; whatever remains is the message. Matches Log's
          existing diary-then-tag pattern (same shape as /prayer, /story).
RESOLVE   Recipient is name-matched (CONCAT firstName,' ',lastName ILIKE) only
          among LOT Community members (Usership/Onyx/Legacy/RND/Admin — the
          same tag gate Sync chat already uses), excluding suspended accounts.
          Scoping to the Community (vs. a full user-base search) is the one
          honest hook available for "Cohort Dating through LOT Community" —
          no dating/matching feature exists in this codebase to integrate
          with instead (verified by full-repo grep before design).
DELIVER   New mail_messages table (senderId, recipientId, message, readAt).
          POST /api/mail-messages creates the row, sync.emit('mail_message',
          ...), writes an audit Log (event: mail_sent, kept off the
          displayableEvents whitelist — mirrors the existing
          direct_message_sent precedent, so Log's public feed stays
          uncluttered by system-internal sends).
SYNC      New `case 'mail_message'` in the /sync SSE fan-out (api.ts) —
          written only to the sender's and recipient's own connections,
          never broadcast room-wide (chat_message's behavior, by design, is
          the opposite). Sync.tsx merges useMailMessages() + this SSE stream
          into the same chronological feed as public chat, tagged "MAIL" with
          a "→ Name" / "← Name" direction label instead of a plain author name.
GATE      Same MAIL_ALLOWED_TAGS gate as Sync chat (Usership/Onyx/Legacy/
          RND/Admin) — LOT Mail is a Community feature, not open to every
          account, consistent with how Sync itself is already restricted.
SCOPE CUT Deliberately did not build a separate Mail tab, MailWidget System-tab
          indicator, or tree-structured reply threading (parentId) this run —
          the task explicitly said "simplest" and "new messages appear in
          Sync," so a thread is just consecutive MailMessage rows between the
          same two users, read the same way DirectMessage already is. Noted
          for a future session if S-2 wants the System-tab indicator.
