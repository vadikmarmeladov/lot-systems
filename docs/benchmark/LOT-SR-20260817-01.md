WHAT CHANGED:
- CalendarEntry gained `time: string | null`; add-entry form gained a native
  <input type="time"> beside the existing text field (still fully optional —
  untimed entries behave exactly as before, preserving the minimalist UI).
- entryKey(date|time|text) — stable dedupe key shared by the sweep and the
  alerted-log lookup.
- Due-time sweep: 30s interval (paused on document.hidden, matching the
  existing EvolutionMilestoneToast convention), computes entries whose
  date+time has passed within a 60-minute ALERT_WINDOW_MINUTES window.
  Dedup is against the Log stream itself (calendar_alert events), not
  localStorage — so an alert fires exactly once even across reloads/closed
  tabs, and a local firedRef guards the same tick from double-firing before
  the log refetch lands.
- On fire: creates a `calendar_alert` Log (event + metadata: date, time,
  text, entryType) — the same createLog/useLogs plumbing calendar_entry
  already uses — and renders an on-widget banner (ACK to dismiss) using the
  codebase's existing terminal idiom: uppercase tracking-widest label, the
  pre-existing `.blink` keyframe for the "// ALERT" tag, opacity-hierarchy
  detail rows, tabular-nums for the timestamp. No new toast/animation
  infrastructure was introduced — everything reuses primitives already in
  index.css and the widget's own Tailwind classes.
- Logs.tsx: new `calendar_alert` branch renders `Block label="ALERT:"` next
  to the existing `calendar_entry` -> `Block label="CAL:"` branch (which now
  also prints TIME when present) — same terse military field-code style as
  the other 100+ handlers in that file.
- selfAssembly.ts: `calendar_alert` mapped to the `calendar` module, mirroring
  `calendar_entry` / `calendar_update`.
