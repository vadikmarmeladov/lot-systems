WIRING / STORAGE / TEST  All 38 *Widget.tsx components mount through the single
  dashboard hub System.tsx (app.tsx:177). Zero orphans — every widget file
  verified to have a live import. Data storage splits cleanly: server/Postgres-
  backed (Memory, Planner, Calendar, GoalJourney, Narrative, UserMetrics,
  SystemProgress, SystemPulse) vs. intentional client-local (Intentions,
  MonthlyPulse, QuantumRandom — localStorage by design, not a wiring gap).
  TESTING: zero automated coverage anywhere under src/ — no test runner is
  even configured (no jest/vitest config, no "test" script). This is the
  single largest systemic gap and predates this session; flagged, not fixed
  (stubbing a test harness for 38 untested widgets is out of safe unattended
  scope for one pass).

LOT AI / SYSTEM / PORTRAIT  AIFeedbackWidget is not an LLM-chat surface — it's
  a rules-engine derivation over already-cached client state (intentionEngine,
  OS diagnostics, profile, logs), zero network calls of its own, no lag risk.
  System.tsx mounts ~40 widgets across 14 named stacks; both previously-
  suspected orphans (GoalJourneyWidget, MoodAnalytics) are confirmed wired.
  PublicProfile.tsx (= Portrait) is fully backend-driven via a single one-shot
  fetch('/api/public/profile/:id') — psychological profile, archetype,
  memory story, correlated indexes, weather/local-time/sound, all real fields,
  no placeholder content.

QIE / MEMORY / STORY  QIE runs client-side against localStorage-persisted
  signals; the 5-min analyzeIntentions() cooldown documented in doctrine
  (below) is confirmed intact in two layers (trigger gate + defensive re-
  check). Memory Engine (/api/memory, staleTime 10min) correctly folds
  plannerContext + quantumContext into the AI prompt ahead of raw logs, per
  standing doctrine. Story = NarrativeWidget → /api/narrative, fully
  deterministic (no AI), server-computed from up to 500 unfiltered log rows
  per request — bounded by the existing limit but with no date-window
  narrowing, a scaling watch-item as per-user log volume grows (not urgent
  today; PROVISIONAL). MemoryWidget is mounted TWICE in System.tsx (lines 490
  and 933) — same cached query key so no duplicate fetch, but two live DOM
  instances is a UI-duplication risk worth a human decision, not fixed here.

  (recordSignal) which folds into the Log — this is the "military
  communications" channel the routine asked about, and it functions as
  designed. There is, however, no SEPARATE widget-impression/usage-analytics
  log (no widget_view/interaction_log table) — usage is only visible
  indirectly through domain signals. Confirmed absent, not a bug, a scope
  decision for S-2.

  Usership-tenure messaging cycle (Month N/12), which is a subscriber-tenure
