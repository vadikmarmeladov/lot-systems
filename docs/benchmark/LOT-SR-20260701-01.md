  The `tags` column is CEO-gated (admin-api.ts canEditTags(): only

  cannot write to `tags` without opening a privilege-escalation path. Roster
  and ration status instead live in `user.metadata.basics` (JSONB, already
  self-service-writable via the same `req.user.set({metadata}).save()`
  pattern used by Settings and theme routes). `tags` stays untouched by this
  module; USERSHIP / AI membership is only ever read, never written, here.

STATE MACHINE — PENDING → ON STRENGTH → STOOD DOWN
  New route file: src/server/routes/basics-api.ts, registered in api.ts
  alongside registerOSRoutes (same pattern).
    GET  /api/basics/state        — read current roster + status
    POST /api/basics/enroll       — roster intake (size, shipping address,
                                     cadence start); requires usership tag;
                                     sets status PENDING
    POST /api/basics/confirm      — PENDING → ON_STRENGTH; appends a
                                     SCHEDULED issue-log entry
    POST /api/basics/stand-down   — ON_STRENGTH → STOOD_DOWN; appends a
                                     STOOD_DOWN issue-log entry; drops the
                                     ration, leaves `tags` (and therefore
                                     USERSHIP / AI) untouched
  Every transition also writes a Log row (basics_roster_intake /
  basics_on_strength / basics_stand_down) via the existing Log model, and
  emits `settings_updated` over sync so /api/me refreshes on all open tabs —
  identical to the existing Settings/theme mutation pattern.

  STEADY STATE is derived, not stored: once the (Month 3) fulfillment engine
  appends a DISPATCHED issue-log entry, the client displays ON_STRENGTH as
  STEADY STATE automatically. No schema change needed when Month 3 lands.
