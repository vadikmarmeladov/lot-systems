01a // WHAT WAS BUILT

M1 — LEDGER & DOCTRINE (public, read-only, live)
  - New public page /open-tab (no auth, no DB query) renders the 23-item
    ration manifest, doctrine lines, price line — verified by Playwright
    screenshot against a locally booted server.
  - In-app "Basics" nav tab wired to a real route (/basics) — was previously
    a disabled stub in Layout.tsx.
  - Shared presentational layer (RationLedger.tsx) so the public surface and
    the in-app tab render an identical ledger — "the ledger is the marketing."

M2 — UPGRADE & ROSTER (state machine, self-service)
  - BasicStatus state machine: NONE/STAND_DOWN -> PENDING -> ON_STRENGTH ->
    STEADY_STATE, tracked in user.metadata.basics with an append-only history.
  - POST /api/basics/upgrade — gated on USERSHIP tag, roster intake (cadence
    start date, optional sizing/fit notes), adds the Basic tag, schedules
    issue #1.
  - POST /api/basics/stand-down — drops the Basic tag and un-dispatched
    issues, keeps Usership/AI. Roster intake form + STAND DOWN control live
    in the Basics tab UI.
  - No live payment gateway exists in this codebase — PENDING resolves to
    ON_STRENGTH within the same request. This is recorded plainly in code
    comments and here, not disguised as a real billing capture.

M3 — ISSUE & FULFILLMENT (load engine, ceiling-checked)
  - Cadence engine (basics-cadence.ts): monthly items ship every issue,
    quarterly items ship on issue numbers divisible by 3.
  - Per-item landed-cost estimates + verifyMargin()/verifyAnnualCycle() —
    runtime-checked across all 12 issues of a cycle: COGS ceiling USD 40.00
    never breached, margin floor 60% always met (worst case 60.1% on
    quarterly-load months, 65.6% on monthly-only months). Costs are
    quartermaster estimates pending real supplier quotes — marked as such.
  - New basic_issues table (migration + Sequelize model) — one row per
    scheduled/dispatched issue, unique per (userId, issueNumber).
  - GET /api/basics/issues (roster's own issue log) and an admin-only
    POST /api/basics/issues/:id/dispatch that marks an issue dispatched,
    promotes ON_STRENGTH -> STEADY_STATE on first dispatch, and schedules
    the next issue — closing the loop the directive calls "NEXT ISSUE
    advances."
  - PRINT MANIFEST control (window.print with a print stylesheet that drops
    nav chrome and controls) — a printable manifest card without a new
    fulfillment vendor integration.

HONEST BOUNDARY: physical fulfillment (a box actually shipping) is outside
what code in this repo can do. The software fully supports the M3 loop —
schedule, ceiling-check, dispatch, advance — but dispatch is an ops action a
human/warehouse process must trigger via the endpoint; nothing here fabricates
a real shipment.
