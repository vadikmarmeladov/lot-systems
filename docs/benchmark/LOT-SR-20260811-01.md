M1 LEDGER & DOCTRINE (cherry-picked, verified, re-wired)
   OPEN TAB public surface: 23-item ration manifest rendered as a categorized
   ledger (NUTRITION 10 / HEALTH 7 / HYGIENE 5 / EQUIPMENT 1), nomenclature +
   spec + cadence only — COGS withheld per doctrine. Doctrine statement +
   USD 100.00/MO price line. Status line (PLAN / RATION). Terminal grid:
   LiberationMono, 2px heavy rule under header, thin rules between sections,
   square corners, inversion-only (bg-acc/text-bac) for active controls.
   Moved the manifest data (RATION_MANIFEST, doctrine lines, price, cadence
   type) from client-only to #shared/constants/basics so the M3 server issue
   engine ships against the exact same item list the public ledger shows —
   client basics/doctrine.ts now re-exports it, zero drift possible.

M2 UPGRADE & ROSTER (new)
   State machine: NONE/STAND_DOWN -> [roster form] -> PENDING ->
   [confirm & authorize] -> ON_STRENGTH -> [2nd issue dispatch] ->
   STEADY_STATE, or ON_STRENGTH/STEADY_STATE -> STAND_DOWN (drops ration,
   retains USERSHIP/AI — Usership tag is never touched by this module).
   State lives in user.metadata.basics (JSONB) — no new table, no schema
   migration. Server: POST /api/basics/enroll (validates USERSHIP tag +
   country/city/address, blocked from re-enrolling while already
   PENDING/ON_STRENGTH/STEADY_STATE), POST /api/basics/confirm (SIMULATED
   authorization — no payment processor call anywhere in this codebase;
   user.stripeCustomerId exists on the model but is unused/unwired, confirmed
   by grep before building), POST /api/basics/stand-down, GET /api/basics.
   Every transition writes a fastify.models.Log entry (event:
   basics_enroll / basics_on_strength / basics_stand_down /
   basics_issue_dispatched) — same Log model and getLogContext() pattern
   used by /api/settings and /api/theme-change, so this shows up in the
   existing activity log without new plumbing.

M3 ISSUE & FULFILLMENT (new)
   Month-by-month load engine: itemsForIssue(n) in #shared/constants/basics
   ships all 20 MONTHLY items every issue, plus the 3 QUARTERLY items on
   issue 1, 4, 7... (n-1 mod 3 == 0). ANNUAL cadence is typed and wired
   (n-1 mod 12 == 0) though the current 23-item manifest has no annual line
   yet. POST /api/basics/issue/dispatch computes the issue, checks it
   server-side against a private COGS table (src/server/utils/basics-cogs.ts
   — never imported client-side, never returned by any API response) before
   shipping: item COGS + $1.50 pack/pick + $2.00 freight, verified against
   the $40 ceiling and 60% margin floor on every single dispatch, not just
   at design time — a breach throws and blocks the issue rather than
   shipping at a loss. Appends to issueLog, advances nextIssueAt +1 month,
   flips ON_STRENGTH -> STEADY_STATE on the 2nd dispatch (demonstrating the
   recurring cadence, not just the first box). Client renders a printable
   manifest card (line items only, no COGS) with a print-only stylesheet
   and a PRINT MANIFEST CARD button (window.print()).

   Computed margin at current pricing (recorded here per doctrine — COGS
   stays withheld from the public tab and from every API response):
   monthly-only issue ~20 items -> landed ~$37.10, margin ~62.9%.
   quarterly issue (all 23 items) -> landed ~$39.50 amortized-equivalent
   input, margin ~60.5%. Both clear the 60% floor and the $40 ceiling with
   the gate as the enforcement mechanism, not just the spreadsheet math.
