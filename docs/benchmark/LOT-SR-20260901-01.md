## MISSION BRIEF

**Objective:** Continue independent work on the Calendar widget without
disturbing its existing minimalist UI. Make it a *reliable* widget: track
actual time (not just date), log everything into the Log stream, and fire
stylish, military-grade event notifications when a scheduled item comes due.

**Constraint:** Keep the visual language exactly as shipped — monospace,
`Block label="X:"` containers, `text-acc` opacity tiers, no new chrome.

---

## GAPS FOUND IN THE EXISTING FOUNDATION

The widget (`CalendarWidget.tsx`) already had: a month grid, date selection,
note/task/call entries written as `calendar_entry` logs, and a QIE signal
(`recordCalendarSignal`) on creation. Three reliability gaps stood between
that and a real scheduler:

1. **No time-of-day.** Entries were date-only — a "calendar," not a planner.
2. **No lifecycle.** Once created, an entry could never be marked done or
   cancelled; the "next up" surface in `System.tsx` would happily keep
   pointing at something already handled.
3. **No alerting.** Nothing watched the clock. A scheduled call at 3pm was
   indistinguishable from a note with no due time — both just sat in a list.

## WORK COMPLETED THIS SESSION

### 1. Time tracking — `CalendarWidget.tsx`
- Added an optional `time` (`HH:mm`) field to the add-entry form, alongside
  the existing note/task/call type picker.
- Entries now carry a stable `id` (`crypto.randomUUID()`, with a legacy-key
  fallback for entries logged before this change so old data still renders).
- Sort order for the month view, the per-date list, and the upcoming feed is
  now `date + time`, so a 9am and a 5pm entry on the same day land in the
  right order.

### 2. Entry lifecycle — done / cancelled
- New event `calendar_entry_status` (`{ entryId, status }`) recorded as its
  own immutable Log entry — the existing `calendar_entry` log is never
  mutated, consistent with how every other module in this codebase treats
  the Log as an append-only signal stream.
- `done` entries stay visible with a strikethrough (so today's completions
  are still legible); `cancelled` entries are filtered out everywhere,
  including the month-grid "has entry" dot.
- `System.tsx`'s "Next:" surface (`upcomingCalendar`) now excludes resolved
  entries instead of continuing to point at something already handled.

### 3. Military-grade event notifications — `CalendarEventNotification.tsx` (new)
- A terminal-grid toast (`[ ALERT ] HH:mm TYPE: text`), styled to match the
  existing `EvolutionMilestoneToast` conventions (border/grid-fill/monospace,
  fade in/out keyframes) rather than inventing a new visual language.
- Watches all pending `calendar_entry` logs on a 30s tick; fires when `now`
  crosses the scheduled time (entries with no explicit time default to
  09:00 local), inside a 15-minute grace window so a missed check doesn't
  fire hours late.
- **Reliability is the point of this component**, not the visuals: every
  fire is written back to the Log as `calendar_event_fired` keyed by
  `entryId`, so the alert is idempotent across refreshes, tab switches, and
  reconnects — it can never double-fire for the same event. `done` /
  `cancelled` entries are skipped, so resolved items never alert.
- Mounted next to `CalendarWidget` in `System.tsx`.

### 4. Log stream rendering — `Logs.tsx`
- `calendar_entry` blocks now show the time when set.
- New `CAL-STAT:` block for `calendar_entry_status` (done/cancelled).
- New `CAL-ALERT:` block for `calendar_event_fired`, showing `[ FIRED ]`
  plus date/time — so a scroll through the Log tab shows exactly when every
  scheduled item actually rang.

### 5. Server — `api.ts` displayable-events allowlist
`GET /api/logs` filters to an explicit allowlist of event types. The two new
event types (`calendar_entry_status`, `calendar_event_fired`) were added to
that list — without this, the client would create the logs successfully but
never see them come back, silently breaking status tracking and notification
idempotency. Caught before it shipped by reading the endpoint, not by
runtime failure.

### 6. Self-assembly signal map — `selfAssembly.ts`
Added `calendar_entry_status` and `calendar_event_fired` → `'calendar'` so
the new signals attribute to the existing Temporal Planner module rather
than falling through as unmapped.

## DESIGN NOTES

**Why status is a new log, not a mutation.** Every other feature in this
codebase (goals, badges, plan_set, intentions) treats the Log as an
append-only event stream — nothing here ever edits history, it just adds
the next fact. Marking an entry done by mutating its original
`calendar_entry` log would be the one exception; recording a
`calendar_entry_status` log instead keeps the Calendar widget consistent
with the rest of the system, and for free it means the "when did I actually
mark this done" moment is itself visible in the Log.

**Why the alert defaults to 09:00 for time-less entries.** A plain date
entry with no time was, until this session, meaningless to notify on — any
hour would be arbitrary. Defaulting to a fixed morning hour turns "someday
this month" entries into a single daily reminder rather than silence, while
anything with an explicit time fires exactly then.

**Why idempotency lives in the Log, not localStorage.** The existing
`EvolutionMilestoneToast` tracks "seen" state in `localStorage` — fine for a
one-device, best-effort toast. A calendar reminder is a different contract:
it should not re-fire from a second tab, after a cache clear, or on a second
device signed into the same account. Writing `calendar_event_fired` to the
Log makes the fired-state a durable, synced fact rather than a per-browser
guess.
