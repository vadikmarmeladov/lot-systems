NOTES — SCOPE AND JUDGMENT (read before shipping)
--------------------------------------------------------------------------------
M1 (OPEN TAB, read-only ledger) and M2 (UPGRADE control, roster intake,
self-service STAND DOWN) are built and GREEN on this branch. M3 (fulfillment:
supplier quotes, printed manifest cards, actual dispatch) is NOT built this
session — it requires real supplier contracts and shipping a physical box to
a real person, which is a business decision, not a code change. Building it
without S-2 in the loop would be guessing at both.

Entitlement design (the judgment call): this repo has no payment processor
anywhere in it — the existing "Usership" plan is granted by S-2 by hand via
the CEO-only tag editor (src/server/routes/admin-api.ts:348,
canEditTags() gated to vadikmarmeladov@gmail.com) after payment happens
outside the app (SubscribeWidget just links out to brand.lot-systems.com).
BASIC follows the identical pattern rather than inventing new billing:
  - /api/basics/enroll lets a USERSHIP member submit roster intake (size +
    shipping) and moves them to PENDING. It cannot grant the Basic tag.
  - The Basic tag (ON STRENGTH, the $100/mo additive charge) is granted only
    by S-2 through the existing admin tag editor — now that UserTag.Basic
    exists, it appears automatically in that UI's Object.values(UserTag)
    loop, no new admin screen needed.
  - /api/basics/stand-down is self-service: a user may only ever remove their
    OWN Basic tag from their OWN record (never grant, never touch another
    user) — this is the one exception to the CEO-only tag rule, and it is
    narrow and safe by construction.
This keeps the money-granting step human-gated, consistent with this
project's own benchmark doctrine ("keep S-2 in view" for judgment, not just
intake classification) and avoids standing up unattested recurring billing
or collecting payment details in an unattended session.

STEADY STATE (the third state machine stage) is left undefined until M3: the
doctrine only distinguishes it from ON STRENGTH by "cadence established,"
which means a first issue has actually shipped. Marking that PROVISIONAL
rather than guessing at a definition now.

Not verified in a live browser: this sandbox has no configured database, so
the Basics tab was validated by the full build gate (tsc + esbuild + server
tsc, all green) and manual review, not a running dev server. Flagging this
per the "test in browser" standard — it was not possible to meet here.
