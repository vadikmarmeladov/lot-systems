05 // WHAT WAS BUILT
--------------------------------------------------------------------------------
No new design work this session — the design was already complete and
BEST-rated (MANIFEST, SR-20260721-01). This session's job was verification and
delivery to the S-2-designated branch, which had not yet received it despite
sharing the same base commit. Feature recap, now live on
claude/dreamy-babbage-be5mdm: CalendarEntry carries an optional `time` field
(HH:mm via <input type="time">); a per-entry status machine (EXECUTE <=15m /
ALERT <=60m / STANDBY same-day-or-<=24h / ELAPSED) drives text color and a
T-minus/T-plus countdown (T-00:14:33 style); a 1s live HH:mm:ss clock and the
next timed event's countdown render in the widget header; a Today panel lists
today's entries with live per-entry countdowns; a military alert overlay
(fixed bottom-right, ACK button, 30s auto-dismiss) fires once per timed entry
entering its 60-minute window and logs a calendar_alert_fired event to Log
(CAL [EXECUTE|ALERT] label). Firing is deduped both in-session (a ref Set) and
against prior Log history (blocks re-fire/re-log across reloads). Logs.tsx
renders calendar_alert_fired via a CAL-ALERT: COCKPIT-RULE block-label
handler — data rows only, no narration. Both new intervals (clock tick, alert
check) are gated `document.hidden || !isRouteActive('system')`, consistent
with Render Isolation across CalendarWidget's System.tsx siblings. The
Backend Whitelist Hygiene fix (calendar_alert_fired added to GET /api/logs's
displayableEvents) is confirmed present and re-verified working on this
branch — without it the write→read loop, including the widget's own
reload-dedup read, silently breaks.
