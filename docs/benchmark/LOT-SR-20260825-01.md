02 // DESIGN
--------------------------------------------------------------------------------
DECISION:    Reuse DirectMessage (Sync's existing 1:1 rail) instead of a new
             "email" table. Add `channel` ('chat' | 'email') and `subject`
             columns. An email IS a direct message — it only needs a
             provenance tag and a compose surface. This is the LOT-style
             "simplest" cut: no inbox model, no thread model, no new SSE
             event — direct_message already covers delivery + real-time.

RECIPIENT:   "to Hitomi" is resolved server-side by case-insensitive
             firstName match against the User directory, excluding self,
             preferring the most recently active match. This is the same
             member pool CohortConnectWidget draws its matches from and
             that /community links out to — so an /email can only ever
             reach a real LOT Community member. Full pattern-based cohort
             scoring (analyzeUserPatterns / findCohortMatches) was
             deliberately NOT reused for lookup: it requires 10+ log
             entries and AI-driven pattern analysis, which would make a
             one-line "/email to X" unreliable and slow for new members.
             The Community/Cohort tie-in is the shared member pool + the
             existing Cohort Connect "Send message" action, which already
             routes into this same DirectMessage/Sync rail.

COMPOSE:     /email joins the existing logTriggers.ts vocabulary (same
             family as /prayer, /qi, /story). Pattern:
               /email to <Name>[.]  <optional message>
             Name captured via regex; remaining text becomes the message
             body. Empty body falls back to a default LOT Email greeting
             (mirrors how /prayer and /story degrade gracefully offline).

SYNC:        No new UI surface required. DirectMessageThread.tsx (the
             existing Sync DM view, routed at /dm/:userId) now tags
             channel:'email' messages with a small "✉ email" marker and
             surfaces the subject as a tooltip. Delivery still emits the
             existing `direct_message` SSE event (channel/subject added
             to the payload), so an emailed message appears in the
             recipient's Sync in real time exactly like a chat DM.

06b // ENGINEERING DETAIL
--------------------------------------------------------------------------------

SCHEMA (migrations/20260825120000_add-direct-message-channel.cjs)
  ALTER direct_messages ADD channel VARCHAR NOT NULL DEFAULT 'chat'
  ALTER direct_messages ADD subject VARCHAR NULL
  Down migration drops both columns. Existing rows backfill channel='chat'
  automatically via the column default — no data migration script needed.

MODEL (direct-message.ts)
  DirectMessage gains `channel` / `subject` fields; create-fields type
  extended with Partial<Pick<... 'channel' | 'subject'>> so existing
  fastify.models.DirectMessage.create({ senderId, receiverId, message })
  call sites keep compiling unchanged (channel defaults to 'chat').

TYPES (#shared/types)
  DirectMessage.channel: 'chat' | 'email', DirectMessage.subject: string|null.
  (src/types.ts carries a duplicate, dead DirectMessage interface not wired
  into any import graph — left untouched, out of scope for this session.)

SERVER (api.ts)
  GET  /direct-messages/:userId  — now returns channel + subject per message.
  POST /log-email  (new)
    Body: { to: string; message?: string }
    - 400 if `to` missing.
    - Resolves receiver: User.findOne({ firstName: Op.iLike to, id: not self },
      order lastSeenAt DESC).
    - Not found → { delivered: false, reason: 'not_found', to } (200, not
      an error — this is a normal compose-time outcome the client renders).
    - Found → creates DirectMessage(channel:'email', subject:'Email from
      <sender>'), emits `direct_message` SSE (existing event, channel/
      subject added to payload — no new SSE plumbing), logs a Log entry
      (event: 'lot_email_sent') on process.nextTick, mirroring the
      direct_message_sent tracking already on POST /direct-messages.
    - Returns { delivered, receiverId, receiverName }.

CLIENT (logTriggers.ts + queries.ts + Logs.tsx)
  New trigger: email-compose (keywords: ['email'], emoji: ✉️/✉).
  useLotEmail mutation → POST /api/log-email (queries.ts).
  Logs.tsx: on trigger, regex `/\/email\s+to\s+([A-Za-z][A-Za-z'-]*)\.?\s*
  ([\s\S]*)/i` extracts name + trailing body from the full log text (same
  extraction style as the existing /qi and /story handlers). Renders a
  "✉ EMAIL:" Block showing DELIVERED / NOT FOUND / FAILED, following the
  exact Terminal Grid result-block pattern used by /silent /freeze /fast
  /phys. Added to the /system help directory.

SYNC (DirectMessageThread.tsx)
  SSE handler now carries channel/subject into locally-appended messages.
  Message row shows a dim "✉ email" marker (title = subject) beside the
  sender name when channel === 'email'. No new route, no new page — Sync's
  existing DM thread (/dm/:userId) is the LOT Email inbox.
