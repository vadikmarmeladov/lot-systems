DESIGN NOTE — what "/email to Hitomi" actually does:
  Log detects the /email keyword (logTriggers.ts, same detector pattern as
  /qi, /assembly, /prayer). Logs.tsx parses "/email to <name> <body>" and
  posts to the existing POST /chat-messages route with a new optional
  recipientName field. The server resolves recipientName against the users
  table (Op.iLike on firstName — the same lookup shape a future directory
  read would use), stores recipientUserId alongside the message, then emits
  the existing 'chat_message' SSE event and writes a Log row (event
  'email_message' instead of 'chat_message', so the ledger can read email
  traffic apart from plain chat). Sync — which is Lot Chat — renders the
  same feed; a message carrying recipientName now shows a "✉ → <name>" tag
  before the text. No new table, no new SSE channel, no new page.
  Log gets a local confirmation block ("SENT → Hitomi — delivered to Sync").

HONEST BOUNDARY — Cohort Dating / LOT Community:
  Neither exists in this codebase (confirmed by search: zero "dating" hits,
  no community route). What exists is behavioral cohort matching
  (CohortConnectWidget, cohort-determination.ts) for medical/paid-tier
  classification — not a social directory. recipientUserId resolution
  against `users` IS the join point such a directory would read from, but
  building that directory was out of scope for "simplest." Marked
  PROVISIONAL, not built: a dating/Community browse UI in front of the
  existing recipientUserId FK is the natural next step, not implied here.
