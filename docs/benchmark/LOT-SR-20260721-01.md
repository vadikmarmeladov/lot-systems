05 // WHAT WAS BUILT
--------------------------------------------------------------------------------
CalendarWidget.tsx — CalendarEntry gained an optional `time` field (HH:mm,
via a <input type="time">, optional at add-entry). New status machine per
entry: EXECUTE (<=15m out) / ALERT (<=60m) / STANDBY (today or <=24h) /
ELAPSED / null, driving both text color and a T-minus/T-plus countdown
string (T-00:14:33 style). A 1s live clock (HH:mm:ss) plus the next timed
event's countdown render in the widget header; a Today panel lists today's
entries with live per-entry countdowns. A 60s check fires a military alert
overlay (fixed bottom-right, ACK to dismiss, 30s auto-dismiss) the moment a
timed entry enters its 60-minute window — and logs it to Log as a new event,
calendar_alert_fired (CAL [EXECUTE|ALERT] label, entry text, date/time,
T-minus at fire time). Firing is deduped two ways: an in-session Set (blocks
re-fire within the mount) and a scan of prior calendar_alert_fired logs
(blocks re-fire — and re-logging — across reloads while an event is still
inside its alert window). Logs.tsx: new CAL-ALERT: military block-label
handler renders entryType/status/date-time/T-minus as data rows only
(COCKPIT-RULE — no narration). Both new intervals (clock tick, alert check)
are gated `document.hidden || !isRouteActive('system')`, per the
Render-Isolation doctrine established in SR-20260719-01/6e5007a — CalendarWidget
lives in System's permanently-mounted widget stack, so an ungated 1s/60s
interval here is exactly the class of bug those commits fixed elsewhere.
api.ts: calendar_alert_fired added to the GET /api/logs displayableEvents
whitelist (see 02-04 FIX LOG) — without this the write→read loop silently
drops every alert log, including this widget's own reload-dedup read.
