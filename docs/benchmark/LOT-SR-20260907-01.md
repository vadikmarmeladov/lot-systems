05 // WIDGET HEALTH AUDIT — FINDINGS
--------------------------------------------------------------------------------
CRITICAL — FIXED THIS SESSION
F1 DEAD FEATURE      MonthlyPulseWidget (the "month-to-month UI reveal") has
                     never fired for ANY user. Root cause: `useProfileView()`
                     (src/server/models/user.ts) whitelists the fields sent to
                     the client and omits `joinedAt`; the shared `UserProfile`
                     type also lacked the field. Client always read
                     `user?.joinedAt === undefined` -> monthNumber stuck at 0
                     -> the mount effect's `monthNumber < 1` guard never
                     passed. FIX: added `joinedAt` to the pick-list and to
                     `UserProfile`. This is the literal answer to "check the
                     15-month reveal": at month 15 nothing showed, for the
                     same reason nothing showed at month 1.
F2 CAP BUG           Independent of F1, the widget's own display logic capped
                     at `Math.min(monthNumber, 12)` forever, so a real month
                     15+ user (this account is 1000+ days in, ~34 months)
                     would have kept seeing "Month 12: One year with LOT... —
                     12 / 12 months" every month after year one, masking real
                     tenure. FIX: message/label/counter now use the real
                     monthNumber; months 13+ render the intended generic line
                     ("Month N. The journey continues.") with an uncapped
                     counter instead of a frozen "12/12".

CONFIRMED — NOT FIXED (documented for a dedicated follow-up session)
F3 SILENT ERASURE, LIVE  The Widget->Memory compression loop (LOT-DOCTRINE)
                     bug class is confirmed active in production code today.
                     The formatLog() that actually runs (src/server/utils/
                     memory.ts, resolved via the `#server/utils/*` subpath
                     import used by api.ts/admin-api.ts) handles only 6 event
                     types. Every `quantum_intent_signal` (~100 QIE signal
                     names, all bulk-inserted under this one event string by
                     /api/quantum-intent/sync), plus `calendar_entry`,
                     `self_care_complete/skip`, and other event types, return
                     '' and are silently dropped from the AI's raw-log
                     narrative before formattedLogs is assembled — no error,
                     no trace. A materially more complete formatLog() already
                     exists in src/server/utils/memory/question-generator.ts
                     (handles quantum_intent_signal via its default branch)
                     but that module is dead code — nothing imports it.
                     RECOMMENDATION: port the default-branch handling into the
                     live memory.ts formatLog(); this is a real behavioral
                     change to AI question generation and deserves its own
                     green-gated session, not a rushed patch here.
F4 UNLOGGED WIDGET   TimeWidget (clock, stopwatch start/pause/reset, 12h/24h
                     toggle, hourly-chime toggle) calls no `recordSignal` /
                     `useCreateLog` anywhere — every interaction is invisible
                     to QIE and Memory. Confirmed by absence of any
                     intentionEngine/queries import in the file.
F5 NO USAGE ANALYTICS  There is no uniform "widget viewed/used" log across the
                     43 widgets. WidgetErrorBoundary (the one universal
                     wrapper, ~30 widgets pass through it) only tracks mount
                     timing and crashes, both client-console-only, never sent
                     to the server. Usage logging today is ad hoc — some
                     widgets call recordSignal on view/interact (e.g.
                     CohortConnectWidget), most do not.
F6 DUPLICATE BADGES  src/client/utils/badges.ts defines `quarter_drop` and
                     `elixir_found` twice each (lines 3214/5501 and
                     4825/6883) — confirmed by esbuild duplicate-key warnings
                     on every build. Each second definition silently replaces
                     the first in the object literal, permanently orphaning
                     one badge variant per key. Left unfixed: badges.ts is
                     ~8000 lines of generated award logic outside this scan's
                     scope, and a rename risks the award-matching logic
                     elsewhere in the file without a full read of it.
F7 NO CODE-SPLITTING  All 42 widgets are statically imported into System.tsx;
                     zero `React.lazy` usage anywhere in the dashboard shell.
                     Production app.js is 716K + ~576K of shared chunks (~1.3M
                     minified JS) loaded up front regardless of which widgets
                     are actually visible/gated for a given user. Direct lever
                     on "optimize widget loading speed."
                     Also: `npm run client:js:build:metafile` does not
                     actually emit or analyze a metafile — the build script
                     ignores the flag — so there is no bundle-composition
                     tooling in place today to size-budget future widgets.
