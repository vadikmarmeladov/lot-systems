UNDERSTANDING + FEATURES BREAKDOWN (current Astrology feature state)
--------------------------------------------------------------------------------
WHAT IT IS:      inlined block inside src/client/components/System.tsx (not a
                 standalone component); math lives in
                 src/shared/utils/astrology.ts (getHourlyZodiac,
                 getWesternZodiac, getRokuyo, getMoonPhase — all pure,
                 isomorphic, no external API, no personal birth data).

INPUTS:          Japanese hourly zodiac animal, Western zodiac sign, rokuyo
                 (six-day auspicious cycle), moon phase name + illumination %.

PERSONALIZATION
(this session):  the client dashboard reading now anchors to the user's
                 saved timeZone (`me.timeZone`, via the new
                 getWallClockDate() helper) when the profile has loaded one,
                 falling back to device-local time otherwise. Previously
                 only the server-side Logs snapshot (getLogContext, added
                 2026-07-27) was timeZone-aware; the live dashboard block a
                 user is actually looking at was not. A user near a
                 day/hour boundary now sees the same rokuyo/zodiac-hour/
                 moon-phase reading on the dashboard as gets written into
                 their Logs entries for the same moment, instead of two
                 readings that could disagree by up to their UTC offset.

WHY IT WAS
BROKEN UNTIL
NOW:             /api/me (fastify.get('/me'), src/server/routes/api.ts:412)
                 returns User.useProfileView(), whose fp.pick() field list
                 never included 'timeZone' — so the client's UserProfile
                 store (src/client/stores/state.ts) always saw
                 `timeZone: undefined`, and the shared UserProfile type
                 didn't even declare the field, so there was no type-level
                 signal the gap existed. Both are fixed: the pick list now
                 includes 'timeZone', and the type declares it.

FRESHNESS:       unchanged — recomputes every 15 min while the tab is
                 visible (staleness fix from prior session), now also
                 recomputes if `me.timeZone` changes (e.g. right after
                 profile load resolves, or if the user edits their saved
                 timeZone in settings while the dashboard is open).

WIDGET
SYNCHRONIZATION: unchanged this session — astrology is registered as a
                 Tier 0 QIE signal source (WIDGET_DEPENDENCY_MAP in
                 intentionEngine.ts), consumed by `system` and `cosmic`;
                 emits one `ambient_reading` signal/day via
                 recordAstrologySignal(), with an `auspicious` (Taian-day)
                 flag. Still exactly the state left by LOT-SR-20260727.

LOGS
SYNCHRONIZATION: unchanged this session — every new Log's `context` JSONB
                 already carries astroRokuyo/astroMoonPhase/
                 astroMoonIllumination/astroHourlyZodiac/astroWesternZodiac
                 (getLogContext, src/server/utils/logs.ts), rendered in the
                 journal's SYS: block (src/client/components/Logs.tsx:365).
                 Verified still intact, no regression.

NOT
IMPLEMENTED
(by design):     any personal natal-chart data (birth date/time/place,
                 sun/moon/rising sign) — the feature stays strictly
                 ambient/environmental (LOT-DOCTRINE D-003). UI stays
                 plain-text/terminal-grid — getMoonEmoji() remains an
                 unused pure function; no emoji were added to the render
                 path (LOT-DOCTRINE D-004, LOT-GENESIS-v1 NODE 1
